## Prefactoring

No broad prefactoring. Reuse the existing policy and guarded resolver; separate only the minimum editor and image support needed on the upstream base. Do not import the preview renderer stack as a shortcut. Treat existing fork seams as reference implementations, not authority to copy unrelated features.

## Findings

1. **Design-relevant: independently buildable branches have no defined composition.** Both series touch the same listing, tree, pane, tabs and route files, while Series 1 opens Markdown read-only and Series 2 edits it. “Determine integration hunks” and “optional shared tabs seam” do not define the outcome when both are applied, the order or responsible integration task, or how a dirty editor behaves when a preview tab, room or conversation is selected. The Controller should specify that each branch builds and passes its own acceptance on the common base without the other branch, name the later integration owner and order without merging the branches during these tasks, and define the combined `.md` selection and dirty-navigation behavior. The combined result should retain the approved editor for `.md`, Series 1 previews for its other types and all T5 save/discard/cancel protections. State which series owns each shared interface and test; if separately developed, fix the exact types, fields and callbacks before parallel implementation and require a real route → browser consumer test after both producers and consumers exist. A later combined-build acceptance must cover both sets and their interaction. This resolves integration within existing decisions; it does not itself authorize a new upstream merge or new flow.
2. **Design-relevant: signed-off drag acceptance is undecided.** Issue #5, its signed-off outside-in flow and T5 acceptance expressly require dragging a tree file into the composer at the caret. The Series 2 dispatch names minimal prerequisites but neither includes nor excludes that result. The Controller must state whether the original T5 result belongs in this cut or is deliberately deferred, with ownership and acceptance for any deferral; do not silently claim full T5 acceptance without it. Retaining it has an existing approved interface and browser test; no new Sascha decision is evidenced merely by extracting it.

## Finite Controller decisions and binding details

- Fix the integration ownership, order and combined behavior described in finding 1, and the drag scope in finding 2. Explicitly state whether a tab strip is required in the standalone Series 2 UI and its navigation contract; do not leave a worker to decide a user-visible behavior. If tabs are used, specify their complete shared props/state and ownership before parallel work.
- Confirm the original level-2 approvals for this cut: `GET workspace-files`, `GET workspace-markdown`, `PUT workspace-markdown`, and `GET workspace-image` under `/api/persistent-agents/:id/`; the server-internal `resolvePersistentRoomWorkspaceExistingFile(policy, rawPath)`; and the ten named `@tiptap/*` dependencies at manifest range `^3.31.3`. T5 already records these approvals; this confirmation fixes their application to the extraction, not a request to re-decide ADR-0002. No other new route, package export or dependency is authorized by this list.
- Use T5's complete authorized public contracts and tool matrix, including all error codes and statuses, as binding; the draft's abbreviated list omits e.g. 500 `workspace_file_error` and 400 mappings. Use the fork's actual exported types and signatures for any adopted internal seams, not merely their names; pin any shared changed interface in the final task. The server response includes `agentId` and `conversationId`, even where browser types only consume a subset.

- Reproduce the four routes' local and mock paired tests, all tool selections, read-disabled policy, root retargeting, symlinks and path restrictions, limits, image headers and no-create conflict behavior. A real browser/server flow with invented data must cover actual tree selection, editing, saving and privacy. Assign its dependency on both route and UI work explicitly. Keep relevant original assertions when splitting mixed tests; do not weaken upstream tests. The independent Tester runs full build and smokes; Sascha's original human image/edit/diff acceptance remains separate.
- The fork lock's `3.32.2` resolutions and the 64-entry inventory are preliminary evidence, not an approved assertion about shipped contents, new delta, licences or bundle size. Produce and review the actual minimal upstream-based lock delta, transitive/optional/peer closure, licences and applicable Omnigent attribution against the artifacts actually shipped. Escalate any additional direct dependency or changed route/export for approval. Do not import renderer notices without a corresponding shipped component.

Do not bring fork factory, ADR, spec or review files into either upstream branch. User-facing documentation belongs in appropriate existing product docs. No real data or services are needed.
