## Findings

1. **Design relevant: protocol is not buildable yet.** The spec names a lock but does not specify its location or host-wide identity, interface, state transitions, contention behavior, timeout and error result, supported operating systems, or cleanup and stale-owner algorithm. Temporary homes and worktrees cannot define separate locks for a host-global callback port. A PID or age alone is not proof that a lock is stale (PID reuse, a slow live holder, and concurrent recovery matter); unconditionally deleting a lock can let two live owners in. Define the exact interface and state diagram, including empty, held, waiting, owner-failed, ambiguous and error states, atomic acquisition/recovery, ownership verification and safe bounded failure. Explain the scope of hosts, users and network namespaces and how unrelated processes are protected.

2. **Design relevant: ownership must follow the actual listener.** The smoke's parent and server are separate processes; a parent-only lock released on parent death can expose an orphan server. Cancellation marks `pending.done` before the underlying flow has necessarily finished; runtime `close()` is not awaited. A revised design must prove the lock remains held through actual listener release on success, failed assertions, startup errors, cancellation and abrupt termination. It must define what happens if the server remains alive or teardown cannot be confirmed; fail closed with a bounded diagnostic rather than unlocking on a guess. Preserve the original flow deadlines and error behavior; define any bounded lock wait outside those deadlines rather than silently extending or weakening them.

3. **Concrete candidate to evaluate, not an approved protocol.** Hold an OS-released test-only exclusive resource in the *same process that can bind the callback*, from before the bind until that process exits, and isolate the three runtime login tests in a process whose exit is awaited. For the smoke, acquire inside its server child before login is possible and retain it until that child's exit; the parent must await confirmed exit on ordinary cleanup. This keeps ownership if the parent dies while its child survives and makes an abrupt owner exit release the resource with the listener. The Controller must choose and specify a cross-platform primitive and exact resource identity, discovery, timeout and error behavior, and prove it does not interfere with unrelated processes. A spare fixed TCP port, an unchecked PID file, or a time-based lease alone does not establish those properties; if no suitable primitive fits the no-dependency scope on every supported platform, escalate rather than silently weaken the requirement. Also account for lingering descendants and runner reuse. This deliberately holds the resource longer than the callback, so its wait bound and impact on concurrent test deadlines must be explicitly validated.

4. **Design relevant: acceptance needs cross-process proof.** Define deterministic barriers and bounded subprocess cleanup for: two real synthetic flows in separate invocations completing with all original assertions; a web smoke and runtime login using the same seam; failure and cancellation before and after bind; parent death with live child, abrupt owner death, and a subsequent acquisition; and a nonparticipant occupying the callback port, whose existing failure remains visible. Verify no stale coordination resource or live listener remains after confirmed teardown, and that a live owner is never stolen. The synchronized negative control must reproduce contention without the seam, preserve the original assertions and deadlines, and use only local synthetic providers. No production code or real external services are authorized. No tests were run in this review.
