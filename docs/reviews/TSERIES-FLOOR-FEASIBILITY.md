# Series Node floor guard feasibility

**Finding: no usable, sound R4 guard is demonstrated.** A small, deliberately incomplete experiment classifies the requested invented cases but also rejects a documented safe form. The existing source includes dynamic loading and mutation that the experiment does not analyze. A complete guard would require substantial new static-analysis and fact-maintenance work, an approved scope and source authority, and a separately reviewed required check; feasibility and cost are not established. Neither this experiment nor this report approves the lock selection or certifies Node compatibility.

## Experiment and measurements

The invented fixture corpus and expected results were written separately from the classifier, but by the same investigator, so are **not independent review**. The prototype uses TypeScript AST and symbols plus hard-coded handling of fixture import and re-export shapes. Its result on both exact floors: direct namespace `fs.glob`, renamed import and one local re-export each above-floor; `fs/promises.writeFile` with literal `{flush: true}` above-floor; one-argument literal `readFileSync` safe; computed access and escaped `fs` unknown. The final eight expected classifications match. The first run classified all three `glob` examples unknown because installed Node 20 types did not resolve `glob`; after adding narrow syntax handling all three were identified. Unknown means rejection in the fixture comparison; the script is not a complete fail-closed program, does not discover every use, and must never be used as a gate.

A second documented safe form, `readFileSync('invented', 'utf8')`, is unknown: **one of two deliberately selected safe controls is rejected**. This is a fixture-level false positive, not a project-wide false-positive estimate. The experiment only recognizes three facts/forms: `fs.glob`, `fs/promises.writeFile` with `flush`, and one-argument string `fs.readFileSync`; unknown options, overloads, globals, instances, CJS, rebinding, escapes, arbitrary re-exports and actual source analysis have no implemented coverage. Two unsupported kinds are exercised as unknown, and the specific real constructs above are not supported; no defensible project-wide unsupported-use or false-positive rate was measured. Fact coverage across all Node APIs is unmeasured and cannot be inferred from three facts.

Primary evidence: Node's immutable [v22 fs documentation](https://github.com/nodejs/node/blob/12fb157f79da8c094a54bc99370994941c28c235/doc/api/fs.md#fsglobpattern-options-callback) records `fs.glob` added in 22.0.0; [v20.10 fs documentation](https://github.com/nodejs/node/blob/a2206640f366cc145b17a2ece66d36bfa75720ee/doc/api/fs.md#fspromiseswritefilefile-data-options) records the `flush` addition; [v20.0 fs documentation](https://github.com/nodejs/node/blob/e7618fb5a5fc25d76b6474e2a6607f04fd6f10e0/doc/api/fs.md#fsreadfilesyncpath-options) documents both read forms, and the [v20.6 snapshot](https://github.com/nodejs/node/blob/9700344c02b8bb927184b0ff4a108ac23bf2be4d/doc/api/fs.md) is the second floor. These are primary research evidence, not an approved authority or an exhaustive capability history. Options and behavior changes cannot be inferred from exported names or type declarations.

## Decisions and remaining work

A guard would need an exhaustive product-owned execution inventory, correct graph and alias/value-flow analysis, a deliberately defined accepted language with fail-closed dynamic and unresolved behavior, and versioned facts for each accepted API, overload, option, global and relevant platform behavior. Existing code shows why this is not a small parser exercise; the corpus and this run do not estimate implementation or annual maintenance effort. A reviewed fact inventory, its update ownership, source authority, supported analysis semantics, handling of dynamic code/escaped values, and an independently reviewed required workflow would all need explicit decisions. If the current code cannot be classified under a sound accepted subset, either product changes or a separately approved alternative/policy are needed. A new tool/dependency may be necessary, but its necessity and adequacy have not been established. Independent Architect review and applicable level decisions remain required; no alternative, floor, acceptance rule or ADR is decided here.

No installs, test suites, gates, product edits, other active worktree reads, real data or actual services were used. Reproducible scratch scripts, invented fixtures and output are retained under ignored `.build/tseries-floor-feasibility/`; archive `.build/tseries-floor-feasibility-evidence.tar.gz` SHA-256 `fafde3648039957b0323a75185c13e875a59fb2485ab009a1bd60c49004f2af7`. Scratch evidence is local and is not part of the commit. The prototype has no production suitability or complete-fail-closed claim.
