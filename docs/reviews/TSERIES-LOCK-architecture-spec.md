## Prefactoring

None. Keep lock generation and validation separate from product code; do not run a nested install over the root tree, change manifests merely to silence validation, suppress lifecycle scripts, or use `npm install`.

## Findings and proposed path

1. **The defect is concrete, but its npm mechanism is not established.** The Series 1 baseline and corrected trees both identify the invalid root 20.19.40, while Series 2's text identifies all three offending consumer edges and its JSON independently reports the invalid root package. The metadata decision supplies verified source and integrity for the existing six entries, not evidence that npm installs them at the intended paths. A successful `npm ci` is not a successful graph check. The probe's nested install has its own `prepare` and changed graph; it is not a valid fix. The exact Arborist cause, including whether this npm version discards or relocates the entries, cannot be inferred from these logs alone.

2. **A deterministic repair is a testable proposal, not yet a proven remedy.** In an isolated disposable clean checkout, a local deterministic generator could start from the pinned base and fork lock inputs, incorporate only the six specifically authorized verified URL/integrity values, and construct the required path-resolved closure. One bounded hypothesis is to place the existing 24.12.2 `@types/node` and its 7.16.0 `undici-types` at the common `runtime/node_modules` ancestor, retaining the existing 20.19.40 root entry and all required metadata, while removing superseded per-workspace copies only if the closure requires it. This uses already pinned versions; no new version or registry exception is approved. First confirm the selected entries and every affected consumer are compatible, no existing path collides, and placement is consistent with lock semantics. Generate twice byte-identically, run a fresh normal root `npm ci` and root `npm ls --all`, and inspect actual resolution from each of the three workspace locations and the root, including undici. Repeat in another clean checkout with the same pinned Node/npm, configuration and platform. If npm does not materialize the intended graph, or any source, collision, metadata or peer requirement is missing, stop and report it. The supplied evidence does **not** establish that this placement works, that it is minimal, or that any compliant repair exists; the Controller must resolve the spec and obtain independent review before treating it as buildable. No nested `runtime npm ci` is part of this method.

3. **Prove the actual candidate rather than a preliminary inventory.** For each standalone branch and later composed tip, record pinned base, manifests, lock inputs and hashes, toolchain, configuration and platform; reproduce the generated lock byte-for-byte, verify all fetched bytes against locked integrity, preserve provenance and explain each path replacement. Run clean normal-lifecycle root install and a zero-exit complete root tree validation without omitted dev dependencies. Trace every direct, transitive, peer and optional edge to its installed path and resolved identity; distinguish legitimate platform-inapplicable optional absences from missing or invalid edges. Check platform/CPU/libc/engine constraints and actual native binaries on each supported target, or explicitly identify unverified targets as incomplete evidence. Audit real built, pruned and packed artifacts and their contents, not just lock entries: identify included packages and versions, source licence files and applicable notices/attribution, including Series 2 Omnigent and Series 1 renderers where shipped. Measure base and candidate installed, pruned and shipped bytes with a stated reproducible method and avoid double counting; report total and delta. Series 1 must also exercise existing jsdom consumers. Preserve all existing acceptance, browser and composition gates; a platform or browser skip is not a pass.

4. **A baseline-delta exception is possible only as an explicit change to acceptance, not as current authority.** Equality of top-level error strings is inadequate: npm can collapse multiple invalid edges into one problem and hide new paths behind the same package. A hypothetical exception would compare independently clean, same-toolchain/platform/configuration installs of immutable baseline and candidate, using a complete machine-readable traversal of every dependency edge (consumer identity and canonical relative path, dependency kind/name/range, resolved identity/version/path, peer context, optional applicability, missing/invalid/extraneous state), not just `problems` strings. It must establish the exact baseline invalid edges, prove each persists unchanged with the same consumers, requirements and resolved identity, and fail on any new, altered, missing or newly reachable invalid/missing/extraneous edge, including peers and platform-applicable optionals; ambiguous, incomplete or unparsable output fails closed. Compare graph and lock provenance as well as problems, validate the comparison with deliberately introduced invalid/missing edges including a new consumer of the same invalid package, and separately prove real build/pack, closure, licences and sizes. Repeat for every supported platform or report uncovered targets as failures. It does not prove the baseline graph is correct, repair the dev type mismatch, or permit unrelated errors, and cannot replace real producer/consumer and behavioral tests. The existing R2 and metadata decisions expressly require dependency-tree validation and stopping on persistent failure; an exception changes that acceptance and is not authorized by the existing level-2 decisions. Ask Sascha before adopting it, with a new reviewed exact specification and classification; never report the original clean-tree requirement green under a delta.

## Narrow decision question

If a genuinely clean root tree cannot be obtained from approved pinned sources and normal lifecycle, should Sascha (A, recommended) retain the clean-tree requirement and defer both cuts until a reviewed repair is proved, or (B) explicitly authorize a narrowly specified baseline-delta exception with the controls above and residual defect recorded? The Controller must first exhaust and report the bounded repair evidence; this review does not select B or approve an ADR.

No code, gate, install, test suite or real data was run or accessed for this review. Existing logs and the named specs were inspected read-only. The pre-existing modified `package-lock.json` was not changed or staged.
