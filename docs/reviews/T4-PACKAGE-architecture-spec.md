## Evidence and binding implementation checks

- The proposal reports exact candidate manifests and lock, 138 distinct new registry artifacts with SHA-512 matching their lock entries, and unchanged lock integrity for xlsx, jsdom, Koffi, JSZip, PDF and canvas. This is candidate evidence, not an installed closure or legal review. Verify the actual release resolutions and all shipped transitive and native artifacts, licenses and notices, including nested packages and the four artifacts with no named notice file in the inventory; retain applicable notices in source tarball and post-prune archive. The existing xlsx hash check is historical. Record file count against the existing 2,500 ceiling; do not silently raise it.
- The generated lock removes `libc` metadata from 23 existing Linux optional entries. Preserve the existing metadata where feasible; otherwise demonstrate with actual target installs and packaged tests that selection and native loading remain correct on supported glibc and musl targets, and explicitly review the resulting diff. Do not infer platform equivalence from lock generation.
- The existing root engine `>=20.6.0` admits versions excluded by jsdom 29.1.1 (`^20.19.0 || ^22.13.0 || >=24.0.0`) and by PDF metadata (`>=20.16.0 || >=22.3.0`). This pre-existing discrepancy is not resolved by a pin or the archive's Node 24.22.1. Keep Node policy unchanged; test the actual installed preview and transitive closure on supported advertised Node versions and the vendored Node before claiming compatibility or releasing. Record exact failures and escalate a real incompatibility for an appropriate reviewed solution; do not assume engines are sufficient runtime proof.
- [GHSA-w5hq-g745-h8pq](https://github.com/advisories/GHSA-w5hq-g745-h8pq) affects candidate nested uuid 8.3.2 and concerns v3/v5/v6 with a supplied output buffer. Inspection of the registry ExcelJS 4.4.0 tarball's `lib` JavaScript found one uuid import, in `lib/xlsx/xform/sheet/cf-ext/cf-rule-ext-xform.js`: it calls v4 with no buffer in preparation/rendering; its parser constructs a model from attributes. The [reader](https://github.com/exceljs/exceljs/blob/v4.4.0/lib/xlsx/xlsx.js) loads and parses the workbook. On this evidence the specified read-only ExcelJS path does not invoke the advisory's vulnerable APIs; this is not a proof about other consumers, other copies, future code, or all vulnerabilities. Confirm the actual installed graph and read-only calls, retain the finding in the advisory record, and reassess if the consumer or resolution changes. No unapproved override or upgrade is implied. Candidate audit also reports tmp 0.2.7 and unzipper 0.10.14; audit the actual closure, including the non-registry SheetJS artifact, without treating an empty audit as proof of safety. ExcelJS's 2023 release is a maintenance consideration, not proof of abandonment.
- K1 must test real installed source tarball and post-prune desktop/archive outside a checkout, including child and package resolution, actual versions, missing child/package/addon and wrong version, native assets and notices. Missing optional runtime installation must fail honestly; it does not waive supported release completeness. It must never invoke the opener. Fake public-route → parent → actual child protocol tests and human real-opening acceptance remain separate; a missing probe blocks a verified Windows packaging claim, not adapter authoring after the other build gates.

Full spec review, Controller package authorization, independent functional review and level-3 conformance remain separate. No partial #4 release.

## Prefactoring

None required for this package decision. Use the existing child, external and file-package ownership seams; do not introduce a new native copier, broad desktop keep rule, public export, dependency or parser to bypass an unproven bound.

## Findings and limits

No architecture blocker to the named package decision on the stated conditions. The CFB pre-traversal feasibility is a concrete unresolved implementation gate, and installed closure, Node compatibility, Word and workbook fidelity, Windows native behavior and platform selection are not yet demonstrated. If CFB cannot enforce the stated limits, the practical next step is a separately reviewed bounded design and any necessary approval, not treating a deadline or heap cap as equivalent. This review used read-only source and metadata inspection; no installation, product test, real file, opener or full gate was run, and no screenshot was created.
