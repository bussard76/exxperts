## Findings

1. **Design-relevant — prior finding 1 remains open: the read and root-policy contract is a requirement to design, not a chosen flow.** The revision now demands fresh policy, `RoomFence`, safe bounded reads and privacy, including Also allowed and shared-server behavior, and names relevant tests. It does not say how a listing, image, text, HTML or parser request obtains its root and path representation, box and fresh policy, how identity/revocation is checked before and after reading, or which bytes a worker receives. This matters: source listing uses `policy.roots[0]` and the removed resolver, while the target's `callFence`, `filesFor`, `inTheBox` and `executeWorkspaceRead` are private; target reads distinguish boxed roots, shared files, beyond roots and the box-fault fallback, and may pass a private copy to a parser. “Use the current path” does not choose an implementable seam or establish how the listing represents multiple authorized roots without changing its contract. Specify each producer/consumer flow, allowed roots and empty/denied/moved/revoked/error results, bounded-read and revalidation points, and public-route checks; reconcile any required new seam with the no-new-contract constraint before building.

2. **Design-relevant — prior finding 2 is partly closed: the policy decision is explicit, but the platform mechanism is not.** The spec now requires refusal with notice and no process start for an unknown association or a program in any room-writable place, requires a fresh check of executable and working directory, and preserves the other approved host-local and pathname rules. That closes the previous *policy choice*, not the implementation contract. Source Windows `ShellExecuteExW` receives the file and a null working directory, while other generic openers do not themselves identify the associated application; the target connector check judges connector inputs and is not an association resolver. Specify per supported platform how the actual association and working directory are resolved, how ambiguity, launchers and changes are detected, how all rooms' writable places are checked, and how that verified result remains tied to the accepted OS dispatch. Define refusal response and UI notice and tests proving no dispatcher is invoked for unknown, unsafe or changed results. If this cannot be achieved while preserving the approved handoff and protection boundary, stop for Sascha rather than guessing or silently dropping a platform.

3. **Design-relevant — prior finding 3 remains open: exact integration contracts and dependency scope are requested, not supplied.** For example, source `workspace-files-api.ts` defines entry fields `name`, `relativePath`, `kind`, `bytes`, `modifiedAt`, `extension` and listing fields `root`, `path`, `entries`; the route adds `agentId` and `conversationId`. Source `workspace-preview` has distinct text/HTML/frame/worker results and limits, while `workspace-open` has specific status/code responses and an allowlist that omits `.excalidraw`. The spec records none of the full per-operation schemas, bounds, format matrix, local/remote/shared states or status-to-UI mappings, and names no actual browser-to-route-to-parser/frame-to-UI test or owner. The source/target package diff also includes server `docx-preview`, `exceljs`, `jsdom`, optional `koffi`, and UI `@aiden0z/pptx-renderer`, absent from the target manifests; the blanket prohibition on new dependencies conflicts with preserving all source formats unless a concrete reconciliation is approved. Inventory the complete feature-specific format, asset and dependency delta against target, choose a permitted implementation or escalate the dependency change, fix the exact producer/consumer fields, error states and bounds, and name the integration test and any slice owners and dependencies. A list of future documentation tasks does not fix these interfaces for a Developer.

The accepted pathname-replacement residual risk is not itself a new finding. No new Sascha decision is assumed or requested by this verdict; level 3 is conditional on the missing design requiring one.
