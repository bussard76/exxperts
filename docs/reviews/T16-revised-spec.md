# T16 revised technical specification

Status: **blocked for implementation**, pending a demonstrated synchronization mechanism or an explicit decision on the unresolved lifetime requirement below. This revision supersedes the R2/R3 transport proposals; it is not a passing architecture review. ADR-0006 records Sascha's option A, visible flow and task-specific no-clickable-fake exception. A fresh independent Architect must review the resulting spec before implementation. Issue #16 remains after Series 1 and does not block it.

## Architecture impact

Level 3: one owner changes the transient decision contract between desktop main and the sandboxed application renderer. ADR-0006 accepted the product flow and data boundary; this technical investigation does not amend it. No file paths, contents or credentials cross the seam. No prefactoring has been established as necessary.

## Accepted behavior

On macOS, Cmd+W in the focused main window requests the active workspace tab's existing close action, including its dirty Markdown guard. No active workspace path, including retained but hidden tabs, is unhandled and invokes the existing main-window close action (normally hide to tray). A dirty prompt, including Save, Discard, Cancel or failed save, counts as handled. While any dirty close, switch or navigate guard is pending, consume repeats without replacing the pending action; the existing guard otherwise replaces it. One request at a time; repeats while pending are consumed. An auxiliary focused window uses its existing close action; no focused window means no action. Preserve the other menu roles, sandbox, navigation policy and other platforms. Failures and unavailable renderers must not silently close or hide the window or discard data.

The owner implements both producer and consumer together: `apps/desktop/src/main.ts` owns the existing application menu, focused window and close-to-tray action; `apps/web-ui/src/App.tsx` owns current pane state, `requestCloseWorkspaceTab` and the dirty guard. The shell's transient request contains no user document data. The UI decision uses current state and the same close path as the tab button. The approved visible flow is in `design/t16-close-shortcut/logic.md`.

## Unresolved technical requirement

The R3 proposal is **not implementable as specified**: it assumes renderer blur runs before an already queued act expression. Neither a main focus-generation check before enqueue nor a renderer focus snapshot/epoch proves this when native blur and refocus are observed in adverse order. A check after a close or prompt cannot undo it. Electron's [BrowserWindow documentation](https://www.electronjs.org/docs/latest/api/browser-window#event-blur) describes blur/focus events and `isFocused()`, but does not specify their ordering relative to renderer tasks or native focus changes; its [webContents documentation](https://www.electronjs.org/docs/latest/api/web-contents#contentsexecutejavascriptcode-usergesture) says `executeJavaScript` evaluates in the page and returns a promise, possibly suspended while loading, without such an ordering guarantee. The desktop package specifies Electron `^43.8.3`. No supported-version/macOS guarantee establishing this order was found; absence from these docs is not proof that no implementation can exist.

A synchronous renderer-to-main request is not a solution by itself: [Electron documents](https://www.electronjs.org/docs/latest/tutorial/ipc#using-ipcrenderersendsync) that it waits for a response, not that native focus cannot change or be delivered late between main's check and the renderer action. An asynchronous invalidation message, focus snapshot, two-phase handshake, shared flag updated only on observed events, or passing a test under normal timing has the same missing proof. A renderer-side deadline also needs a defined common clock and cannot by itself establish focus authority. Neither navigation nor destruction tokens eliminate that race.

The required property to establish is: from the shortcut's captured main-window focus lifetime until the instant immediately before the renderer first closes a tab or opens a prompt, **any actual native focus loss** (even if followed by refocus and delivered to either process late) invalidates that request. The same authority must invalidate on navigation start, document/window destruction or replacement, and expiry at 1,000 ms. A candidate must identify an atomic synchronization or native invalidation primitive and authoritative supported Electron/macOS evidence for every ordering it relies on, including how it prevents an unobserved native blur in the check-to-action interval. It must also preserve sandbox/navigation policy and ADR-0006's data boundary. No candidate established here meets that bar; do not implement R3 or claim a guarantee based only on observed test timing.

## Decision and next step

**Recommendation A:** Controller commissions a bounded investigation of a supported native/Electron primitive and its documented ordering, then revises this spec if proven. This retains the approved contract without a new product decision; do not start implementation until the independent Architect passes the revised spec. If no primitive can be established, return the question to Sascha rather than silently weakening the lifetime requirement.

**Alternative B:** Ask Sascha whether the product may accept a narrower, explicitly described best-effort focus guarantee: check current focus and observed generations immediately before dispatch and before fallback, but a delayed renderer close or dirty prompt can occur after an unobserved blur/refocus. This changes the described failure behavior and needs an explicit product decision and architecture review; it is not already authorized by option A. The exact revised contract and its risk need approval before implementation.

**Alternative C:** Defer #16 and retain current window behavior until a safe implementation is available. This avoids introducing the shortcut and needs the Controller/Sascha to decide the product outcome; it does not block Series 1.

Decision question for Controller: pursue A first, or present B and C to Sascha if A is exhausted? No redundant approval of ADR-0006's already accepted flow is requested.

## Acceptance evidence for any eventual protocol

Tests use invented data and exercise the actual macOS menu callback, real shell producer and real sandboxed app-renderer consumer together, with controlled barriers at the candidate's actual synchronization and side-effect points. Record supported Electron/macOS versions and cite the authority establishing ordering separately from the tests. A test must expose a native focus loss before the side effect while delaying its observation in main and renderer separately; include blur/refocus within 1,000 ms and permanent loss, and assert no tab close, dirty prompt, window close or hide. The harness must prove the real invalidation mechanism is exercised, not merely replace the consumer with a stale result or inject an already delivered blur event. If it cannot control or demonstrate those native ordering conditions, state that limitation; the test does not establish the guarantee.

Cover delayed dispatch and result, 1,000 ms expiry before action, navigation start/new document, destroyed and replaced window, missing entry point, exception, malformed response, and no focused window; invalid requests cause no renderer side effect and no fallback. Check one outstanding request, repeats and pre-existing close/switch/navigate prompt without replacement. Exercise active and hidden retained tabs, empty pane, Save/Discard/Cancel/failed save, auxiliary close and actual close-to-tray fallback through the producer/consumer seam. A separate UI test checks the same close guard as the × button. Use a single owner for both ends; an implementation spec must fix exact typed request/result fields, lifetime, clock and registration/disposal rules before parallel work. Sascha separately verifies the packed Mac shortcut. These checks cannot substitute for the missing ordering proof.
