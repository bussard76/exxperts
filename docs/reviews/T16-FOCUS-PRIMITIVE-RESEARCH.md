# T16 focus lifetime primitive research

Outcome: **no proven supported primitive found; implementation remains stopped.** This is a bounded investigation, not a proof that no possible implementation exists. R5's recommendation A retains ADR-0006 unchanged. A proven candidate still requires a revised specification and a fresh independent Architect review. No Mac, timing experiment, product code, real data, or test suite was used.

## Scope and evidence

The property under investigation is R5's actual native focus lifetime from shortcut capture through the instant immediately before the renderer first closes a tab or opens a dirty prompt: **any** intervening focus loss invalidates the request, even if focus returns and neither process has yet observed the loss. Navigation start, document/window destruction or replacement, and expiry at 1,000 ms must also invalidate it. The accepted visible behavior and no-clickable-fake exception are already decided in ADR-0006; neither is reopened here. Sources read: R5 `docs/reviews/T16-revised-spec.md` at `497b2ed`, R4 `docs/reviews/T16-R4-architecture-spec.md` at `bf324dc`, and ADR-0006 at `497b2ed`.

The code at the research base `9111063fdd58ad96ad27f9bd1967dbe5a8de2a13` puts the menu, focused native window and hide-on-close in `apps/desktop/src/main.ts:245-285,634-670`; its navigation policy is at `:217-242`. The window has `sandbox: true` and no preload. The current tab close and dirty guard belong to `apps/web-ui/src/App.tsx:584-653,8680`. The desktop package declares Electron `^43.8.3` (`apps/desktop/package.json:20`), while its committed lock resolves **43.8.6** (`apps/desktop/package-lock.json:1890-1893`). The range is not a guarantee about later versions. The version-pinned Electron source below is evidence about 43.8.6, not a platform ordering promise across every allowed future version.

Electron's [process model](https://www.electronjs.org/docs/latest/tutorial/process-model#the-main-process) places Node and window ownership in the main process and the page in a separate renderer; main cannot directly execute the renderer's DOM or React action. [Sandbox documentation](https://www.electronjs.org/docs/latest/tutorial/sandbox#renderer-processes) says the sandboxed renderer has no Node environment, and even a sandboxed preload has a limited module set. Adding a narrow preload is not itself unsandboxing, but IPC does not create the missing ordering. No paths, contents, or credentials may cross the proposed seam.

## The check-to-action interval

Let C be the final check and A the renderer's first close or prompt side effect. A is a page operation, not the main process's send or acknowledgment. Between C and A, the renderer can be scheduled away or the native focus can change independently. A focus loss L, followed by refocus R, can occur in C < L < R < A; or L can precede C while notifications to both processes are delayed. A current focus snapshot can be true at both ends, and a generation advanced only when an event is delivered can still be unchanged at A. The side effect is already real by the time any later validation rejects a response. Checking immediately before the call makes the interval smaller, not atomic; even a renderer-side clock check has a nonzero interval to A.

Electron 43.8.6 defines [`blur` and `focus`](https://github.com/electron/electron/blob/v43.8.6/docs/api/browser-window.md#L251-L257) as events when focus is lost and gained. Its [macOS `IsFocused`](https://github.com/electron/electron/blob/v43.8.6/shell/browser/native_window_mac.mm#L464-L466) reads `[window_ isKeyWindow]`; Apple describes [`isKeyWindow`](https://developer.apple.com/documentation/appkit/nswindow/iskeywindow) as the current key status, not an uninterrupted lifetime. Apple says [`resignKeyWindow`](https://developer.apple.com/documentation/appkit/nswindow/resignkey%28%29?language=objc) notifies the responder, delegate and notification center, and the [delegate callback](https://developer.apple.com/documentation/appkit/nswindowdelegate/windowdidresignkey%28_%3A%29) is main-actor isolated. These sources do not promise that OS-level loss cannot precede notification delivery, or order that notification against a separate renderer task. Key-window status and actual OS focus must not be silently equated beyond what those sources establish.

## Candidates considered

| Candidate | What it can do | Why it does not establish the requirement |
| --- | --- | --- |
| Main/renderer focus snapshots, epochs, blur messages, or two-phase arm/act | Reject loss already observed and check current focus. | A delayed native event or loss/refocus produces the counterexample above. Electron's [`executeJavaScript`](https://github.com/electron/electron/blob/v43.8.6/docs/api/web-contents.md#L1416-L1430) schedules evaluation in the page and may suspend during loading; it does not serialize OS focus with A. A renderer blur handler may itself run after A. |
| Synchronous renderer-to-main IPC and native `isKeyWindow` check | Blocks the renderer until main responds; a sandboxed preload could expose a narrow operation. | Electron [documents waiting for the reply](https://github.com/electron/electron/blob/v43.8.6/docs/tutorial/ipc.md#using-ipcrenderersendsync), not an OS-focus lock. Loss can occur after the check or reply and before A; an earlier unobserved loss/refocus is also invisible. Blocking main until renderer acknowledgment risks deadlock and still does not hold a WindowServer focus transaction. |
| Native AppKit observer/addon on main, native event tap, or main-thread critical section | Can observe some native events or query current key status, and a main-process addon can use native APIs. | No cited supported API makes every actual focus change update a shared lifetime before the renderer can act, nor holds off WindowServer focus changes through an action in another process. AppKit callbacks/serial queues serialize their own work, not the OS transition and a renderer's React side effect. Native event interception is not established as covering all loss causes or focus ordering; permission, sandbox, and completeness remain unproved. |
| Shared memory, atomics, compare-and-swap, locks, or a native generation counter | Can make cooperating writers/readers agree on a memory order. | They cannot make an undelivered OS event update the flag. Even a correct atomic check followed by a JS action permits loss between them; a lock helps only if the OS focus transition is a cooperating participant, which is not established. A native addon in the sandboxed renderer is not a supported escape from this constraint; moving state to main still requires a proven seam. |
| Execute the whole check and action inside one native/main callback or a native transaction | Would be promising only if the actual side effect and all focus transitions shared an authoritative atomic serialization point. | Main owns `NSWindow`, while the renderer owns the DOM/React action. A main callback can queue page work, not synchronously perform that work as part of an AppKit focus transaction. No supported Electron/AppKit primitive found joins these operations or prevents external focus changes across processes. A hypothetical Chromium/Electron patch or changed product ownership is not a supported primitive proved here. |
| Defer commit, rollback, or check after action | May suppress a later fallback or hide some delayed results. | Opening the dirty prompt or closing the tab is itself the first side effect; a later rejection cannot make it never have happened. An optimistic UI with an actual prompt also fails the specified property. |

## Lifecycle, expiry and no-focus conditions

A feasible *partial fail-closed protocol*, not an implementation recommendation or a proof of focus authority, would bind a single request to the exact main window and document, with a single monotonic 1,000 ms deadline, invalidate on observed navigation start and destruction/replacement, reject malformed/unavailable/late responses, and permit fallback only on an explicit current unhandled result after rechecking the same identity, focus and deadline. No focused window produces no action; a focused auxiliary window uses its existing close action. It must contain no user document data. This reduces stale-result risk but **must not execute the renderer action** under the unresolved R5 guarantee.

Electron 43.8.6 [documents navigation event order](https://github.com/electron/electron/blob/v43.8.6/docs/api/web-contents.md#L24-L50) and [`did-start-navigation`](https://github.com/electron/electron/blob/v43.8.6/docs/api/web-contents.md#L311-L337); [`will-navigate` excludes programmatic and in-page navigation](https://github.com/electron/electron/blob/v43.8.6/docs/api/web-contents.md#L246-L276). [`destroyed`](https://github.com/electron/electron/blob/v43.8.6/docs/api/web-contents.md#L498-L500) and object identity can reject observed stale work. None specifies ordering against already queued renderer actions at the instant of actual start/destruction, so lifecycle invalidation needs its own proof at A, not merely a main-side token. A replacement document must not inherit authority; document and window identities, registration/disposal and canceled navigations need exact definitions in a revised spec.

A timer message alone can arrive late. Even with a specified common monotonic clock and a renderer check at C, preemption until after the deadline before A leaves an expiry race. A clock conversion, a single clock domain and atomicity between the deadline decision and A must be demonstrated; 1,000 ms is not a reservation of focus or execution time. Destruction, missing entry point, exceptions, no focus and timeout must fail unavailable without a close, prompt or fallback, as R5 specifies. These mitigations do not prove the stronger lifetime property.

## Tests, gaps and next sources

Controlled tests should run the real macOS menu-to-sandboxed-renderer seam using invented data, place barriers at the proposed authority and A, and force native loss/refocus with delayed observations in each process, permanent loss, deadline, navigation start, destruction/replacement and no-focus cases. They should assert no close, prompt, hide or fallback on invalid requests and establish that the actual mechanism ran. Tests can expose a counterexample or corroborate a documented guarantee on the tested builds; passing observed schedules cannot establish all possible ordering. No Mac is assumed available, and none was used here.

Targeted next research, if pursued: ask Electron/Chromium maintainers for a **supported, versioned** ordering or transaction that couples OS focus loss and renderer execution; inspect the exact Electron 43.8.6 / corresponding Chromium native focus and renderer scheduling paths and Apple WindowServer/AppKit guarantees for all focus-loss causes; identify a documented atomic linearization point covering A, navigation and expiry. Source inspection alone describes an implementation, not a supported future-version contract. Any candidate must explain how actual native loss, including one not yet delivered to either process, participates in that point; how it keeps the existing sandbox and data contract; and how it handles the check-to-A interval. No such point is established here.

If no proof is established, return the already documented alternatives to Sascha: R5 **B**, explicitly approve a narrower best-effort guarantee and its delayed-action risk, with a revised contract and architecture review; or **C**, defer #16 and retain current window behavior. Either is a product decision; a new security or architecture decision is also necessary if a proposed mechanism changes the accepted sandbox, data boundary or responsibility. The worker makes neither choice. ADR-0006's accepted behavior needs no renewed approval merely to continue technical research.
