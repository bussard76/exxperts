## What the new evidence establishes

Read-only local checks confirmed `orca status --json` reports app PID 3106685, process 3106720 is its child and has `/dev/ptmx` fd 81 with `tty-index: 55`; PID 3403150 is a child of 3106720, is its own session leader, has controlling device pts/55, and its initial environment contains the matching project worker terminal handle. The worker record is for `workhorse2` and the Orca terminal is connected and non-orphaned with a pty ID and incarnation ID. These are valuable independent kernel and Orca facts, stronger than a handle on a sampled process alone. The reported gate PID 3407266 was already gone when rechecked, so its complete live ancestry and eventual classification could not be revalidated in this review. Do not reuse its PID as a live identity.

This chain establishes that a real shell session is attached to a PTY owned by an Orca app descendant. In a trusted, non-adversarial environment it is strong evidence of a registered worker terminal and can support a private Linux level-1 solution. It does **not yet prove** that the opaque Orca `ptyId` and incarnation correspond to that particular master fd, or that every process under that shell belongs to this project: the only observed link to the terminal handle is an environment value, which can be inherited or copied, and a worker shell can start a foreign-project gate. A terminal list entry's `status` field is absent here; `status !== "exited"` is not sufficient liveness proof.

## Blocking verification and bounded implementation

1. **Terminal binding.** Demonstrate an existing authoritative mapping, scoped to the same host and Orca runtime incarnation, from the exact active worker terminal `ptyId`/incarnation to the particular OS PTY master or session leader, or document and verify an existing Orca invariant that the app directly creates this session leader with the unique handle in its initial environment and that unrelated terminals cannot be assigned that handle. Check worker host, project worktree and unique terminal, active terminal incarnation, app PID/start time, app-to-master-owner ancestry, fd-to-PTY device, leader SID/PPID/controlling TTY, and leader handle. Read the leader's handle only; no other environment value may be emitted. Recheck both terminal incarnation and the kernel identities around the sample. Matching a copied handle alone, including a copied handle on a second real Orca PTY, must not exempt it. The opaque `ptyId` observed here was not mapped to tty-index by the available evidence.
2. **Nested and foreign gates.** A worker-owned terminal proves execution ancestry, not project ownership of a gate run from another project. Specify and verify how every gate boundary on a candidate chain is detected and positively associated with this project, including an inner foreign gate, and fail closed when that cannot be established. A command name, common lock, cwd substring, terminal handle, stale PID-only slot or inherited worker identity alone cannot distinguish all cases. Without such evidence leave that branch foreign. A gate that exits or changes while inspected is unknown. If this prevents attribution of the observed gate, report the coverage gap rather than claim the defect resolved.
3. **Race and spoof scope.** Kernel start ticks and boot ID prevent many PID-reuse errors; parent PID and start order checked before and after capture provide bounded evidence, not an atomic tree snapshot or protection against malicious same-user alteration. Require verified project provenance at the terminal root and gate boundaries, and no changed PPID/start identity on recheck. Every unknown process with sampled CPU counts foreign; a broken or unparseable complete sample causes suite `wait`, never a falsely quiet period. Same-user spoofing cannot be ruled out by a user-controlled environment variable; if it is excluded by the accepted trust model, say so explicitly, and still test accidental inherited handles and foreign gates.

If both bindings are demonstrated using existing interfaces, this is a level-1 pass candidate: no new gate/worker record, no threshold, calibration or caps changes. The positive result is exclusion of the verified worker-owned descendants whose ancestry and gate ownership are continuously established, including temporary-checkout descendants. Unrelated processes, foreign gates, ambiguous trees and unverifiable roots remain foreign; this does not guarantee exclusion of all genuine descendants, particularly after reparenting or fast exit.

## Exact private local and SSH probe contract

Execute the same static probe on the target host through the existing `onHost` local shell or SSH path. The Controller obtains target-host Orca status and terminal metadata using the matching Orca environment; `orca status --environment` exists, but the returned app PID must be proven to refer to the same OS host and boot being sampled, otherwise ownership is unknown. Never query local `/proc` for a remote PID. Do not send raw environment, cwd, commands or process arguments across the seam.

Probe output is newline-delimited JSON with exactly one `header` `{kind:"header",version:1,bootId:string}`, any number of `node` `{kind:"node",pid:positiveInteger,ppid:nonnegativeInteger,startTicks:decimalString,sid:nonnegativeInteger,tty:integer,pcpu:number|null,handle:string|null,gate:"project"|"foreign"|"unknown"|"none"}`, any needed `pty` `{kind:"pty",ownerPid:positiveInteger,ownerStartTicks:decimalString,fd:nonnegativeInteger,ttyIndex:nonnegativeInteger}`, and exactly one `end` `{kind:"end",version:1,nodeCount:integer,ptyCount:integer,bootId:string}`. `pcpu` is finite and nonnegative only for the exact top-30 CPU sample rows; `null` means ancestry-only. `handle` is the one selectively read Orca terminal value only on session leaders; no environment or handle output goes to the public verdict, journal or logs. `gate` may be `project`, `foreign` or `none` only when the selected existing detection source proves it; otherwise use `unknown`. The Controller associates the response with the selected host and a same-host status/terminal snapshot; it must not accept probe-supplied project ownership without its verified source. Any required source not fixed by the revised spec is a blocker, not a permissive default.

The probe reads `/proc/<pid>/stat` around the final `)` and extracts PPID field 4, session field 6, tty field 7 and start-time field 22; it reads only the named NUL-delimited handle from leader environments and PTY master `fdinfo` tty-index. Collect and revalidate the complete ancestry and device association on the target host, with fixed finite node/depth/time bounds, double-reading identity fields and boot ID. Duplicate IDs, invalid types, missing markers, count mismatch, changed boot or identity, truncation, unavailable `/proc`, failed `ps`, SSH failure or an incomplete required source cannot yield a clean sample. Known sampled CPU for unknown rows counts foreign, including unreadable environment/cwd, fast exit and PID reuse. If CPU rows themselves cannot be trusted or recovered, return suite `wait` with a generic reason and prevent quiet calibration; preserve read-only admission, PSI, memory, load, gate slot formulas, >=5% sampling cutoff, top-30 limit and strict unrounded `foreign > threads/4` threshold.

## Test and rollout conditions

Use test-only Node preloading with `syncBuiltinESMExports()` in a disposable copy of the Controller and invented config/state. Intercept `execFileSync`/`spawnSync` at the existing `onHost` and Orca command seam to supply controlled probe and Orca results; exercise actual `capacity.mjs --verbose`, parser, attribution and verdict. Redirect every journal/state/slot write into the disposable copy and fake remote SSH entirely. No production fixture option, environmental override or new public export. At least one test must run the actual generated producer against an isolated synthetic proc/ps/Orca adapter and pipe its actual output through the actual consumer; verify the adapter does not generate the wire output itself and no real network or Controller state is touched. If a private injection method is needed for this, specify it before implementation and verify it does not change the production interface.

Test local and SSH host and boot separation, two concurrent PTYs, exact terminal incarnation and app/PTY mapping, worker and project gate descendants outside a worktree, unrelated same-user process with a copied handle, another Orca PTY carrying an inherited handle, foreign gate under a project terminal, nested gates, unknown gate ownership, unreadable environment, stale worker, ambiguous terminal, fd reuse, changed TTY/SID/PPID/start time, PID reuse, fast exit/reparent, malformed/truncated output and unavailable host. Check unknown load and strict thresholds immediately below, equal to and above the unrounded boundary, and verify equal pressure inputs retain identical PSI, gate-slot and calibration results. The independent Tester reviews the complete candidate and these public-command tests.

For read-only live verification use an independently running gate and suppress **all** state, slot and journal writes, including SSH-side writes; do not start a gate or change caps. Record timestamps and limitations, and report unavailable if write suppression or identity cannot be proven. Back up and hash project Controller files before deploying only the independently tested candidate locally; restore exact files on failure, without touching other projects or external systems.

## Outside-in and prefactoring

The public capacity verdict and the synchronized sample are the outside-in evidence; the relevant flow is Orca/worker identity + target-host probe → proven tree/gate ownership → foreign sum → unchanged pressure and calibration. No new UI design artifact or prefactoring is required. If implementation is split, fix the wire fields and proof sources first, record dependencies and test the actual producer and consumer together.
