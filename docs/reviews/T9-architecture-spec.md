## Prefactoring

None is required as a separate architectural step. Refine the read and frame-message contracts at their existing seams, then implement and verify them within the approved decision; avoid a broader viewer rewrite.

## Findings

1. **Design-relevant: identity and read bounds.** The new `.txt`/`.json` and framed byte paths in `room-settings-routes.ts` use `guarded.stat.size` followed by `readFileSync` on the pathname, without the HTML path's descriptor identity checks and re-resolution. A file replaced after the guard can yield different bytes, and a file growing after the size check can exceed the intended bound. Define the same workspace/policy protection and a bounded descriptor read with before/after identity and current-policy checks; specify errors and race tests. The existing `chmod` acceptance must still succeed while real content changes return `file_changed`.
2. **Design-relevant: frame navigation and byte delivery.** `WorkspaceFramedPreview.tsx` accepts every `frame-ready` from the frame's `contentWindow` and sends a copy of the file with target `"*"`. A frame retains its window identity across navigation, so a navigated document able to send that message can receive the bytes; source equality alone does not establish the original document. Specify a delivery protocol that prevents bytes reaching a navigated document, with an adversarial browser test including repeat-ready and navigation, or present the concrete residual risk for Sascha's decision. HTML's accepted self-navigation risk does not by itself decide this additional parent-to-frame delivery.
3. **Decision needed: renderer and host action scope.** Option A (recommended): record the two pinned renderers and their opaque-origin frame, explicit allowed OS-open extensions, accepted navigation risks and required controls in an accepted ADR; retain blocked external resources and existing workspace/local-action rules. Option B: defer the new frame renderers and expanded host actions pending a narrower decision. Sascha's acceptance of PPTX's single maintainer with containment is relevant evidence, not a substitute for specifying and accepting these contracts. Prepare the proposed ADR using `docs/adr/0000-template.md`; this review is the only file authorized for this worker to write.
4. **Design-relevant: buildable contract and evidence.** The issue names the desired states and tests but does not fix the byte/status message schema, lifecycle, timeout, cancellation or parallel ownership, and the outside-in artifacts are absent at the reviewed revision. Add these to the spec and link the approved design evidence or explicit exception. Test valid, empty, invalid, multiple-frame and hostile inputs through the actual route, parent and frame; tests must cover concurrent tabs and direct frame loads. Do not treat mere precision as a product redesign.
