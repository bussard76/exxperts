## Findings

1. **The selection change is measurable; current breakage is not established.** Root declares Node types `^20.0.0`; TUI has no direct Node types edge but inherits `types: ["node"]` from `runtime/tsconfig.base.json`. The compatibility report measures clean base TUI selecting root `@types/node` 20.19.40 and `undici-types` 6.21.0, versus runtime ancestor 24.12.2 and 7.16.0 in the candidate; the other three runtime workspace builds select the ancestor too. TUI's compiler trace confirms this selection. Under Linux x86_64, glibc 2.39, Node 22.23.4/npm 10.9.9 the candidate builds all four workspaces, passes 570 TUI tests and 27 selected actual coding-agent consumer tests, and has byte-identical TUI dist and packed tarball against base. One strict downstream consumer of the packed declarations compiles. The diagnostic `node:fs` `glob` import fails against base types and passes against candidate types, although that API arrived in Node 22 and is not used by current TUI sources. This demonstrates future exposure, not an existing product defect. Identical declaration text does not guarantee identical interpretation in other downstream type environments; `skipLibCheck` in the build further limits the inference. The examples configuration fails with the same three diagnostics on both trees, and full runtime tests were not established as passing.

2. **A finite level-2 solution is possible in principle, but the spec lacks the necessary guard and floor proof.** A one-time source search, clean build, identical declarations, a test suite, or compilation using root 20.19.40 types alone cannot ensure >=20.0.0/20.6.0: even later Node 20 APIs may exceed the exact minor floor, and tests need not execute every path. Revise the spec to name the owner, exact source/build scope, implementation and ongoing required CI/check entry point of a guard that fails closed on all statically referenced Node builtins and members, globals, imports/re-exports, aliases, and dynamic/computed accesses that it cannot establish safe. Map accepted APIs and relevant overload/options to their actual introduction versions against each module's declared floor; flag unverified APIs for explicit review, and provide a controlled, reviewed mechanism for updating the mapping. The guard must cover transitive product code within the change's affected runtime scope as specified, not claim to certify arbitrary third-party code. Demonstrate positive controls including `node:fs` `glob` and a post-20.0/20.6 Node 20 API, plus aliases and unresolved dynamic access; a known floor-compatible API must pass. If coverage cannot be achieved without an unauthorized dependency, manifest or workflow change, classify that proposal separately and stop; do not silently substitute a heuristic search or rely solely on execution coverage. This is a design requirement, not permission to implement a particular new tool.

   For each actual standalone graph and composed graph, record toolchain, actual `tsgo --traceResolution` and Node/undici resolution from every affected consumer, compare emitted and packed declarations with the appropriate pinned base under identical settings, inspect differences, and compile actual packed declarations in representative real downstream consumers with `skipLibCheck false` under their supported type environments. Run TUI build and relevant TUI/real consumer tests with exact Node 20.0.0 where the standalone TUI contract applies and product/coding-agent tests with 20.6.0, plus normal supported current Node targets. Report a toolchain that cannot run on a declared minimum as a concrete blocker, not a pass; distinguish build-host requirements from runtime tests if the spec explicitly establishes them. Exercise supported OS/CPU/libc and native/optional cases using the applicable platform matrix; missing environments remain unverified, not accepted. Negative runtime tests cannot prove every unexecuted path safe, hence the ongoing guard. Full independent Series gates and actual closure are still necessary.

3. **The preserving shield is not established.** The shield probe's normal clean `npm ci` discarded both TUI-specific root-version lock entries, while installing the ancestor pair. It did not establish why and stopped before compiler/build checks. Do not specify this shield as a working alternative. The ancestor proposal must state root 20.19.40/6.21.0 and the four expected runtime consumers 24.12.2/7.16.0, exact lock paths and the two already approved URL/SRI identities, and assert source equality, compatible edges, absent collisions and no intervening shadowing. Enumerate implicit and explicit consumers in each actual graph, including direct undici and its lookup from the selected types. Unexpected consumers, paths, type versions or public changes stop for review. R2's deterministic generation, independent reproduction, normal-lifecycle clean root `npm ci`, zero-exit `npm ls --all`, stable lock and closure checks remain binding.

4. **The 154 missing metadata entries remain a separate acceptance blocker.** I verified the retained inventory SHA-256 `63f1422fcc5e2c5dbfc8674c5c7e3e6d110eb01b532607dea279cb5918d64b69` and counted 154 entries, 74 production-selected, 54 appearing in reported UI sourcemaps and 1,911 checked regular files with no recorded missing/different files. Twenty entries have matching cached SRI in root-lock alternatives and six more have matching nested-lock pins: 26 total, three mapped to UI sources. These corroborate byte identity for the observed current installation, but do not establish historical origin, the missing path's locked integrity, or bytes fetched in the removed clean candidate installs. The remaining 128 have no matching pinned alternative in the ten examined lock snapshots; 66 are production-selected and 51 appear in reported UI sources. Cache identity and self-hash are not independent authority; the examined snapshots are not proof no authoritative metadata exists elsewhere. Extra postinstall files, modes, links and native execution were not proven by the regular-file comparison. The analysis lists the initial inventory hash incorrectly: the actual `placement-missing-metadata.json` SHA-256 is `d2f8ee035f53f1505a4f253c3cbdc34ea4f133b88db7adbfcbdc0ce4c4209b36`.

   For each applicable path in each actual graph, retain an auditable mapping to an already authorized, independently pinned original source and exact artifact digest, and verify retained fresh-install fetched bytes and relevant installed/shipped artifacts against the required locked integrity. Matching pins for the 26 are candidates for a separately reviewed finite reconciliation, not authorization to edit metadata or waive provenance. For the 128, locate independently authoritative original pins and perform the same comparison; if unavailable, stop. An external attestation or newly chosen registry cannot replace missing locked integrity under existing rules without a separately classified and decided acceptance/source-policy change. Neither category inherits authority from the two approved type-package sources.
