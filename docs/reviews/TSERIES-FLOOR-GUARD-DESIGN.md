## Existing seam and affected scope

Root `package.json` and coding-agent declare >=20.6.0; TUI, AI and agent manifests declare >=20.0.0. The compatibility probe found TUI and the other three runtime build configurations switch from root Node types 20.19.40 to ancestor 24.12.2, and Node 24 types admit `node:fs` `glob`, introduced in 22.0.0. No current TUI use or runtime defect was established. `runtime/tsconfig.base.json` has `types: ["node"]`, `skipLibCheck: true`; TUI emits declarations. Node 20 types alone also include post-20.0 and post-20.6 APIs. Root `npm run build` builds the four runtime packages; `.github/workflows/ci.yml` runs build and smokes on Node `20`, meaning a moving latest Node 20, not the exact minima. `coding-agent/src/main.ts` actually consumes TUI and AI, and agent imports AI; `coding-agent/src/utils/photon.ts` uses `require("fs")` while TUI uses both bare and `node:` builtins and namespace imports. This is evidence of the seam, not an exhaustive graph.

The minimum proposed conservative analysis scope is **all shipped product-owned source** of `runtime/packages/{tui,ai,agent,coding-agent}/src`, plus any product-owned transitive files imported or re-exported into these builds, including generated sources and shipped JS assets that execute in Node. Analyze each independent package at its own manifest floor; analyze shared paths at the strictest floor of every owning entry point, not only at a consumer's looser floor. Enumerate package exports/bin, build configs, relative/workspace imports, conditional exports and generated/shipped artifact lists on each actual standalone and composed graph. An unresolved local edge, nonliteral import/require, unknown file type or shipped Node-executable file outside inventory stops the check pending classification; do not silently exclude it. Third-party packages, native addons, arbitrary user extensions, eval-generated code and OS behavior are outside this static guarantee and require separately recorded runtime/platform and provenance evidence. Browser-only assets require an evidenced exclusion, not filename guesses. The scope is a proposed minimum, not an established exhaustive manifest: a revised spec must resolve product entry points and boundary before adoption.

Series 1/2 UI contracts, outside-in design exports, privacy, and real producer-to-consumer composition remain as required by their R2 and R4 reviews. This tool does not access user data, introduce product data flows, or alter those interfaces; the parallel owners and exact shared contract remain the R4 ones. The guard itself has no producer/consumer shared product fields. An independent real Series producer/consumer test on the composed tip remains required; unit fixtures for this guard cannot replace it. No feature design folder or logic diagram was supplied for this guard; its proposed data flow is source inventory → parser/resolver → floor facts → diagnostics/exit status → required CI check.

## Candidate fail-closed interface and mechanism

A possible internal build-tool interface is one repository-root command, `node tools/check-node-floor.mjs`, returning 0 only when every inventoried file and use is proven within its applicable floor, and nonzero with deterministic path, line, floor, normalized capability, reason and evidence identifier for every unknown, unsupported, above-floor or parse/resolution error. Missing/corrupt metadata, unknown syntax, unrecognized alias, stale inventory, unavailable parser or unsupported compiler semantics also fail. The check reads repository sources and a committed, reviewed facts file offline; it must not contact a service or inspect user data. No automatic allow-by-default, unreviewed suppressions, catch-and-continue, or exception based solely on passing tests. Exact CLI, locations and integration require a new accepted spec; these names are illustrative and not authority to create them.

Use the already installed pinned TypeScript compiler API only if its exact selected package, syntax support, module resolution and availability under the clean authorized graph are verified. It is a development dependency today, but importing it from a new check still needs a reviewed tool/interface decision; `tsgo` is not automatically interchangeable with the TypeScript JS API. Use AST plus symbol resolution for runtime imports, exports, namespace/default/named imports, destructuring, assignment aliases and re-exports, CJS `require`, literal dynamic `import`, globals and global objects, constructed instances, property chains, option names and overload arguments. Normalize `fs` and `node:fs`, distinguish third-party `glob` from `node:fs`, and distinguish local shadows from Node globals. Track aliases through local/workspace data flow; unknown or escaped builtin objects/functions, rebinding, mutation, reflection, prototype operations, unresolved receiver type, dynamic module names or computed property names fail rather than disappear. Literal computed properties may normalize to the same member. Dynamic code (`eval`, `Function`, loaders) and cross-boundary value escape require rejection or an explicitly verified narrower policy, not an assumed safe result. `any`, casts and declaration types alone cannot prove the runtime value or option shape. Unknown spreads, input-controlled options, callbacks or overload discrimination fail if they may affect an API's floor. A guard that flags every unresolved case can be sound only for its precisely defined accepted language and assumptions; no evidence yet shows it will be usable on this repository, or that arbitrary JavaScript behavior can be classified completely.

The mapping needs records per capability and behavioral variant, not just per exported name. A proposed record is `{id, module, receiver, member, kind, signature, optionPath, constraints, minVersion, platform, evidence}`: `kind` distinguishes export, global, instance/static member, argument/overload and option; `signature` and `constraints` describe accepted argument forms and optional conditions; `evidence` identifies an immutable source commit, path and exact section. An explicit accepted-form allowlist for each floor means absent entries or uncovered parameter shapes fail, even if a parent method is known. Separate metadata for newly accepted overloads/options and platform constraints; versions compare semantically, including patch and backports, not lexical strings. A method's introduction does not prove all its options, behaviors or later changed defaults existed then. Runtime constants, inherited methods, return-object members, property reads and builtin globals need equivalent treatment. A table and checker must themselves have reviewed independent tests and no inferred completeness from `@types/node` annotations.

## Evidence and maintenance of facts

Official Node release-tag documentation is a useful primary source but must be pinned to immutable commits and independently authorized as source authority. Exact tag targets observed via read-only `git ls-remote`: v20.0.0 `e7618fb5a5fc25d76b6474e2a6607f04fd6f10e0`, v20.6.0 `9700344c02b8bb927184b0ff4a108ac23bf2be4d`, v20.10.0 `a2206640f366cc145b17a2ece66d36bfa75720ee`, v22.0.0 `12fb157f79da8c094a54bc99370994941c28c235`. For example [Node 22 fs documentation](https://github.com/nodejs/node/blob/12fb157f79da8c094a54bc99370994941c28c235/doc/api/fs.md) explicitly records `fs.glob` added 22.0.0; [Node 20.10 fs documentation](https://github.com/nodejs/node/blob/a2206640f366cc145b17a2ece66d36bfa75720ee/doc/api/fs.md) records `fsPromises.writeFile` option `flush` added 20.10.0. [20.0](https://github.com/nodejs/node/blob/e7618fb5a5fc25d76b6474e2a6607f04fd6f10e0/doc/api/fs.md) and [20.6](https://github.com/nodejs/node/blob/9700344c02b8bb927184b0ff4a108ac23bf2be4d/doc/api/fs.md) are floor snapshots, not evidence for every later change. Both examples must fail both floors; the option case catches silent ignored behavior, not just missing symbols.

Node's Markdown includes `added` and history annotations, but histories are prose, occasionally cover multiple release lines, and do not constitute a proven complete formal inventory of overloads, options, defaults, globals or platform behavior. No exact complete authoritative per-minor machine-readable dataset has been established here. Merely comparing exported names on floor binaries cannot validate options or behavioral differences. Proposed maintenance: pin authorized Node commit hashes and reviewed source excerpts in a checked-in fact inventory; for every new code form or changed Node type/compiler/source version, require a reviewed fact addition citing exact immutable floor/release evidence, with an independently authored positive and negative fixture. An offline deterministic schema/duplicate/reference checker rejects missing source IDs, invalid versions, ambiguous variants and stale checksums; changing pinned evidence, inventory scope, floors or checker requires independent review and documented ownership. If the source is silent, conflicts, lacks provenance, or evidence does not cover an option, fail and investigate; manual assertion is not proof. Initial audit of all current uses and maintenance burden remain unmeasured. This mechanism is a plausible finite allowlist for reviewed forms, not proof that the entire Node API can be automatically mapped or maintained economically.
