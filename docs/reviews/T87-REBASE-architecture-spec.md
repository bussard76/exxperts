## Findings

1. **Design-relevant: the migration has no executable authorization and read contract.** The task asks the Developer to reconcile protection but chooses no call/data flow. In the source, `workspace-files` calls the old `resolvePersistentRoomWorkspacePath`; `workspace-preview` opens paths directly or passes an absolute path to `runWorkspacePreviewWorker`; the image route has a separate reader. At the target, `roomFence` judges moved/refused roots, closed places and access; `executeWorkspaceRead` chooses box-mediated bytes and a private copy where appropriate. Define per operation how fresh policy, room/conversation identity, folder selection, fence, OS box and a stable bounded read interact, including fail-closed behavior when the box cannot safely read, policy changes during a read, denied and missing targets, empty lists and unreadable files. Specify which bytes the parser receives and how results are revalidated. Require public-route tests for protected and unprotected states, path escapes and symlinks, protected names and app data, folder replacement, revocation and concurrent replacement, with invented files.

2. **Design-relevant: the host opener's interaction with the newer program-start protection is unspecified.** The source invokes platform openers and Windows ShellExecute with a guarded path; a file association can run a program outside the room box. Target `connector-start-check.ts` explicitly refuses a connector whose executable, package or working folder can be changed by a room, checking real paths and current writable places. The spec must trace the actual platform opener, associated application and working directory, define how unsafe or unknown program resolution fails closed, and prove the selected mechanism with fake dispatchers and writable-place fixtures. Do not assume the connector check applies to OS associations or that the OS opener itself is the final program. If enforcing the protection cannot preserve the accepted original-file/assigned-application flow, or a protection exception is proposed, stop and obtain Sascha's decision with concrete options; do not silently omit a supported platform or accept a new execution risk.

3. **Design-relevant: contracts, test ownership and dependencies are not fixed.** Source `workspace-files-api.ts` defines listing entries (`name`, `relativePath`, `kind`, `bytes`, `modifiedAt`, `extension`) and root/path/entries, while preview and opener use other payloads and a worker protocol. The task does not say which source interfaces survive target integration, their exact response/error contracts, format matrix, local and remote states, supported target platforms, bounded parser/renderer behavior or precise dependency inventory. Record these for each route and producer/consumer, including empty, unsupported, ambiguous and failure cases; reconcile source's added dependencies and bundled assets against 0.16.1 and the instruction that no new dependency is authorized. Name and order any build slices, and prove at least one real browser → route → parser or frame → UI flow as well as the fake-opener route tests. Existing ADRs and the signed design constrain the answer; they are not an exact migration contract.

No suite was run; this is a pre-build review. The accepted OS-open pathname replacement race is a documented residual risk, not by itself a new finding. A concrete newly exposed protection bypass or a change to that handoff is different and needs the decision described above.
