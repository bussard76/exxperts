## Findings

1. **Real compiler shadowing, not a demonstrated runtime failure.** Base root `package.json` includes `runtime/packages/*` and declares `@types/node ^20.0.0`. The base lock has root Node types 20.19.40 and undici-types 6.21.0, and separate copies 24.12.2/7.16.0 under each of `runtime/packages/{agent,ai,coding-agent}/node_modules`. Their manifests require Node types `^24.3.0`. TUI declares no Node types edge, but `runtime/packages/tui/tsconfig.build.json` extends `runtime/tsconfig.base.json`, whose `types` is `["node"]`; TUI uses Node globals and imports, for example `src/terminal.ts`. Its build runs `tsgo`, emits declarations, and root build includes TUI. No base TUI or runtime-ancestor copy exists in the lock. Series 1's retained blocker reports actual installed resolution from TUI changing from root 20.19.40/6.21.0 to runtime ancestor 24.12.2/7.16.0. I independently inspected its candidate lock: those ancestor paths exist and the TUI-specific copies do not. Series 2 reports the same base resolution and candidate lock/installed closure; its candidate TUI lookup is an inference, not a retained actual measurement. Measure it in a fresh actual candidate. The three named runtime workspaces and TUI are all four workspace builds inheriting that base configuration; `coding-agent/tsconfig.examples.json` also extends it. Search and trace additional type references and consumers, nested packages, and direct/transitive undici resolution in each candidate; these four are not a proof of exhaustive closure.

   Node and undici type packages describe compile-time APIs; they do not upgrade the Node executable or install a runtime implementation of those APIs. Node 24 declarations can allow source to typecheck using APIs absent on the supported Node 20 floor, and can alter emitted public declarations or downstream checking. `skipLibCheck` is enabled, so a clean compile alone does not prove declaration compatibility or runtime availability. No actual incompatible call, changed emitted declaration, runtime breakage, or clean candidate TUI compilation is established here. Compare actual compiler resolution and emitted declarations against the pinned base with identical toolchain and options, inspect new or changed Node API usage and public declarations, run TUI build and relevant TUI/runtime consumer tests on the supported minimum Node and other supported targets, and check actual packed declarations with a real downstream consumer. Record versions and paths; a successful check is evidence for its target, not all platforms. Do not silently raise the supported Node floor.

2. **A preserving alternative is plausible, not proven.** Keeping the original three 24.12.2/7.16.0 pairs at their original workspace paths, with only the approved metadata, leaves TUI reaching the root pair if npm materializes those paths. Earlier independent Series evidence in `a2651f9` says normal root `npm ci` did not materialize the required workspace graph and `npm ls --all` failed even with metadata; its mechanism is unknown. Therefore this is not an accepted solution. A TUI-specific root-version copy under `runtime/packages/tui/node_modules` could theoretically shield TUI from the common ancestor, but has no manifest edge and may likewise be discarded; it changes lock placement and must not be assumed installable or authorized. Moving only one of the two packages cannot by itself restore all expected type and direct undici resolutions; inspect both from every consumer and from the selected types package. A manifest/tsconfig dependency or typeRoots change creates a different interface and is not authorized by this lock-only decision. A narrow disposable experiment using only pinned source identities, unchanged manifests, normal lifecycle and no npm install may compare these hypotheses; a lock topology is not proven until normal clean `npm ci`, zero-exit `npm ls --all`, and actual compiler and package resolution show the specified results. No such experiment was run in this review. The minimum viable preserving placement is unknown.

This requires the compatibility checks in finding 1, actual exhaustive consumer and graph checks, and independent architecture review before adoption. A compatibility failure or an unexplained public declaration/runtime change stops the attempt; do not label the shadowing harmless based on `npm ls` or `skipLibCheck`. Check both standalone graphs and later the composed graph. Any other source, version, dependency, policy, or product contract change returns for separate classification. Both Series remain locked until Controller adopts the reviewed solution.

4. **The 154 pre-existing missing-metadata entries are unresolved.** Series 2 reports 154 unchanged base installed lock entries without `resolved`/`integrity`; this review has not independently counted or verified those entries. Unchanged base status alone proves neither source identity nor fetched-byte integrity. R2 requires retained original source metadata, full closure and source provenance, verification of fetched bytes against locked integrity, and no invented metadata; it does not authorize fabricating 154 entries or waive this requirement. An authoritative per-identity provenance record tied to the exact actual fetched bytes and identity may establish where bytes came from, but an external record alone is not verification against a missing *locked* integrity. The Controller should map each applicable entry and specify independently auditable evidence, including original authoritative source, exact artifact digest, installed artifact mapping, applicability, and how the required locked-integrity check is satisfied. If a valid existing lock or other already authorized pinned source supplies exact matching fields, propose a finite reviewed reconciliation without inventing them; otherwise the existing requirement remains unsatisfied. A new source authority or substituting external verification for locked integrity is a change to the current acceptance/source policy, not an automatic level-2 waiver.
