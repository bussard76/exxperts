## Prefactoring

None prescribed. Extend the existing grant serialization and fence locally; do not introduce a separate store or bypass RoomBox. Resolve the two design findings in the spec first.

## Findings

1. **Identity representation and supported filesystems are not specified.** “Platform-appropriate” and “suitable … including restart” leave implementers unable to agree on a persisted contract, to distinguish an unreliable identity from a valid one, or to know which local folders can be granted. A practical candidate is a private tagged/versioned record with platform and exact decimal-string values obtained using bigint filesystem metadata: device/volume, file/inode identifier and a reliable stable creation/birth discriminator, compared together with the existing canonical path. This is a candidate, not a claim that Node's fields provide a reliable discriminator on every platform or filesystem: availability, uniqueness, precision, reuse, mounts, network/cloud providers and Windows file-ID behavior must be established for each supported combination. Mutable directory mtime/ctime cannot serve as a stable creation identity. If the available APIs cannot establish the stated lifetime, fail closed rather than claiming support; do not add a native dependency without separate authorization. Specify the exact tagged shape and strict decoding, qualification and unknown/error behavior, capture and recheck against the same directory object where supported, and the actual platform/filesystem support and refusal boundaries. Independent native validation must report measured and unmeasured combinations, including restart and replacement, rather than infer Windows or macOS results from Linux. The spec must also address identifier reuse and the residual assurance of the chosen discriminator; matching path or an unchecked zero/rounded/default ID is insufficient.

2. **Refusal and explicit reauthorization are not buildable from the stated contract.** Rejecting an old/malformed root during normalization makes the target reader return `null`, which the existing listing contract treats as an unconfigured empty workspace. Conversely, `PUT workspace-default` with a root creates a grant, while a settings-only save omits the root; the location UI supports both picker and typed path. Specify a retained but unusable legacy/malformed state and its existing refusal mapping, never the empty state, and define which existing user actions constitute explicit selection (including selecting the same path or typing it), so policy rewrites, startup and settings-only saves cannot capture replacement identity. Ensure successful same-path reselection is recognized even if a save response is lost: the current UI's recovery checks only whether the path changed. Define behavior when capture cannot establish a trustworthy identity, while preserving private metadata and no new public contract unless separately approved.

Required validation after a corrected spec: through actual selection/save, persisted policy reload and public guarded routes, verify a selected disposable folder survives restart; replacement at the same path, old/missing/malformed/unverifiable identity and identity change during bounded read or before open fail without data, parser or dispatch; then explicitly reselect the same path and succeed. Verify settings-only saves never refresh identity, metadata survives permitted policy rewrites and stays out of views/logs, shared shelf behavior is unchanged, and current policy/room/conversation and RoomBox invalidation tests still pass. Independent Tester runs the specified full migration checks; no tests, builds, gates, product changes or vulnerability reproduction were performed for this review.
