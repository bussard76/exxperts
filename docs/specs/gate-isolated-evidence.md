# Isolated smoke gate evidence — proposed specification

Status: proposed for independent architecture/spec review, 2026-11-06. No implementation is authorized until that review passes. The Controller selected a bounded level-2 internal evidence design; review must assess whether the runner-to-controller evidence protocol or changed execution flow crosses a level-3 boundary. No product feature, dependency, route, store or public export is proposed. Sascha's gate decision is recorded in `docs/coordinator.md` and `~/controller-exxperts/decisions.md` (2026-11-06).

## Contract and trust

The existing `npm run smokes` output and summary stamp stay unchanged. A controller-invoked runner additionally writes one private UTF-8 JSON completion record on a dedicated inherited descriptor, not stdout or stderr. The descriptor is supplied only to the runner process, never to the spawned smoke processes; neither descriptor nor any identity value is passed in their environment. Smoke output, including forged JSON, runner-shaped summaries and arbitrary multiline failure tails, therefore cannot constitute evidence. The controlling parent creates and reads the pipe, imposes a bounded record size, and requires one complete JSON document followed by EOF; missing, malformed, duplicate, oversized or extra bytes fail closed. A fresh unpredictable per-invocation run identifier ties the record to its invocation. This protects against accidental or spoofed *output*, not hostile same-user processes reading another process's memory or descriptors; same-user malicious code is outside this design's trust model and must not be represented as cryptographic authentication. The reviewer must decide whether that trust assumption is acceptable. No evidence file or descriptor is reused across runs.

The runner constructs the record from its actual selected names and final result collection only after every selected smoke has closed and reporting is complete. Schema, exactly: `{ "version": 1, "runId": "<identifier>", "commit": "<full git object id>", "complete": true, "selected": ["<basename>", ...], "failed": ["<basename>", ...], "selectedCount": N, "failedCount": F }`. Names are exact sorted unique basenames ending `-smoke.ts`; counts match arrays, failed is a subset of selected, and no other fields or duplicate JSON keys are accepted. The runner checks its actual HEAD and clean tracked tree before and after the run, against the expected commit supplied by its parent; inability to establish either means no valid completion record. The controller independently performs the same checks before and after each phase and immediately before push, including staged changes, tracked changes and HEAD; inventory is independently discovered from the integration tree at that commit. Generated ignored or untracked build artifacts are not treated as tracked changes; untracked smoke files and a changed discovered inventory are red. An interval change that is restored before observation cannot be excluded by these checks; independent review must assess whether stronger isolation is needed. Run identity and commit are compared to the parent's expected values, not trusted merely because the record contains them.

A full record must enumerate precisely every discovered smoke, no filter; an individual record must enumerate precisely the one requested name. The runner's exit must be 0 iff no smoke failed, and 1 iff at least one failed; signals, other codes and contradictions are red. Any record without a complete normally exited runner is red. Full suite evidence with zero failures passes; one or two exact failures requires every failed name to complete and pass in a separate one-smoke run at the same unchanged commit; three or more, unknown results or any individual failure stays red. Preserve the parallel log, each isolated log, validated record, statuses, commit and disposition for review. Any failure to persist required evidence is red.

## Execution and push

Support only the exact existing intended `VERIFY_CMD` value `npm run build && npm run smokes`; reject other values before verification, with a clear red result. Also verify the checked-out package's `smokes` script is exactly `node scripts/run-smokes.mjs` before using the runner directly with the private descriptor: this retains its actual command and arguments while avoiding a package-manager child that may close the descriptor. The reviewer must assess this equivalence and the npm environment difference. The controller invokes build and unfiltered runner sequentially in one `full-gate.sh` invocation, preserving its host-wide flock and `GATE_SLOTS=1` across both; build exit zero is an independent prerequisite, and the runner is never started after build failure. Isolated reruns use the same host-wide full-gate lock and exact filename selection, and controller verifies no other filename matches the substring filter. Browser gate and existing push hooks remain in place. Verify HEAD, tracked tree and inventory again after all gates and before the actual push; fail closed on any failed check. The existing dry-run precheck is not a real push. No live wave or full gate is run during implementation.

## Public-entry-point test plan

Use invented smoke fixtures and temporary git repositories, a local fake remote and fake build/gate commands; never invoke a production wave, model API or external service. Test the runner command and complete integration-wave entry point, not private functions. TDD each observable behavior, with a red test before its minimal implementation:

1. Zero failures: complete exact inventory, successful build, valid record and one real push to the local fake remote; summary text remains unchanged.
2. One and two parallel failures: exactly those names rerun separately, all individually green, records and logs retained, push occurs only afterward.
3. Three failures: gate red and no real push even if their individual runs pass. An individual red, missing record, nonzero build, non-smoke failure or contradictory runner exit each prevents push.
4. Missing, truncated, malformed, oversized or duplicate record; duplicate keys/names; wrong version, count, subset, identity or commit; missing, extra or filtered selected names; interruption or invalid status: each red. Inject forged valid-looking completion records and summary lines in a smoke's stdout/stderr and failure tail; they never become evidence.
5. Change HEAD, tracked staged or unstaged contents, or smoke inventory before, during and after full or isolated runs and before push: each red. Test an individual filter matching multiple names, and an isolated record naming the wrong smoke.
6. Verify concurrent fake full gates cannot overlap while the build and parallel runner remain within one host-wide lock; verify unsupported `VERIFY_CMD` is rejected rather than partially executed and verify the browser gate and push-hook failures remain red.
7. Verify the normal runner retains human-readable failure details, summary stamp, retries and skip reporting, and without private evidence invocation remains compatible. Check script and UI typechecks, affected script suites, and any browser specs actually affected through `gate`; repeat affected suites after merging `origin/main`. Independent Tester performs the full gate and review.

## Open review decisions

- Does the isolated inherited descriptor adequately protect against spoofed smoke output in the stated cooperative same-user threat model, or is a stronger OS isolation boundary required?
- Are direct runner invocation and the verified package script equivalent enough to preserve `npm run smokes`, including its npm environment? If not, specify a reliable inherited channel through npm without changing behavior.
- Is the private runner/controller completion record a level-2 internal contract or a level-3 protocol/data-flow change? If level 3, stop pending Sascha's accepted ADR.
- Is the stated tracked-tree/inventory checking sufficient for unchanged-commit evidence, or must the execution environment prevent transient modification?
