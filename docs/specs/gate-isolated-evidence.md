# Isolated smoke gate evidence — revised proposal

Status: proposed, blocked pending Sascha's acceptance of [ADR-0004](../adr/0004-gate-completion-evidence.md) and a fresh independent spec review. This spec describes recommended option A, not an accepted design. Review: `origin/agents/gate-evidence-review:docs/reviews/GATE-EVIDENCE-architecture-spec.md` at `077004f`.

## Architecture impact

Level 3: the smoke runner, a narrowly scoped npm-script wrapper, and the Controller's wave supervisor exchange a new versioned completion/status protocol over local IPC. The Controller uses the validated record and independently observed process statuses as authoritative integration evidence. This changes an interprocess contract and authority/data flow; it adds no product route, store, dependency or public export.

## Ownership, source and trust

The Controller owns the integration checkout exclusively from before build through the final push; no other cooperative writer or test intentionally modifies tracked source. Check HEAD, index and tracked working tree, and smoke inventory before/after build, each full or individual invocation, browser gate, and immediately before push; every Git error is red. Compute expected inventory from tracked commit entries, compare actual directory including ignored/untracked names, reject missing, extra, duplicate, symlink or nonregular smoke entries, and never hard-code the current count. Persistent changes at phase barriers are red. Endpoint checks do **not** detect a transient edit restored between observations or prove uninterrupted byte identity; ownership is a cooperative constraint, not OS enforcement. A transient-edit test must demonstrate this residual limit, not assert detection.

The Controller supervisor creates a fresh private directory and parent-bound local IPC endpoint for each invocation, with exclusive creation and no stale path or symlink reuse, and owns cleanup. The Linux-only evidence mode is separate from the portable ordinary runner. Channel separation prevents smoke stdout, stderr or failure tails impersonating records; it is not cryptographic authentication against same-user processes, modified runner, filesystem interference or `/proc` inspection. Fresh unpredictable invocation IDs correlate messages, not authenticate hostile same-user code. The locator and run ID must be removed from every smoke child's environment and descriptor map, including retries; npm lifecycle and wrapper are cooperative trusted code under the same limitation.

## Execution and evidence contract

Accept only `VERIFY_CMD` exactly `npm run build && npm run smokes`; reject any other value before partial execution. Run actual `npm run build` then actual `npm run smokes`, with default parallelism and full npm pre/post lifecycle and environment, under one `full-gate.sh` call and its fixed host-wide flock and `GATE_SLOTS=1`. Build must independently exit zero before smokes start. The existing npm smoke script invokes a narrowly scoped wrapper which launches the real runner with inherited standard streams and unchanged npm environment, waits for its actual close status/signal, and reports that status on the supervisor's private channel; it mirrors the runner exit so npm's lifecycle behaves normally. The wrapper strips evidence locator/identity before runner smoke children are spawned, not from the runner itself. The runner separately emits its completion record after all results and human reporting complete. The Controller must independently observe build exit, runner close status, runner record, wrapper completion, npm exit including pre/post lifecycle, supervisor completion and outer gate status. Only a normal runner exit 1 matching a valid failed set, with all other enclosing stages successful, is recoverable; npm lifecycle failure, spawn error, signal, outer gate or supervisor failure remains red. The specific wrapper/status protocol must be independently reviewed for preserving npm behavior; no direct Node bypass or environment approximation is allowed.

An npm exit of 1 can be expected when the runner exits 1; it cannot by itself distinguish that failure from another npm failure. The wrapper must report its own normal completion after observing the runner, and the supervisor must verify npm's supported lifecycle behavior with tests and reject any case where another lifecycle or npm failure could be confused with the runner result. The precise mechanism for proving that distinction remains an explicit spec-review question; if it cannot be proved, the result stays red. A successful runner requires npm exit zero, including postsmokes.

Per invocation, the runner emits exactly one canonical UTF-8 JSON document: fixed key order `version`, `runId`, `commit`, `complete`, `selected`, `failed`, `selectedCount`, `failedCount`; version 1; complete true; full expected commit; arrays of sorted unique exact basename strings ending `-smoke.ts`; integer counts exactly matching arrays; failed a subset of selected. The Controller rejects duplicate keys, noncanonical representation, extra keys/bytes, malformed UTF-8, wrong IDs, version or commit, duplicate or invalid names, and mismatched counts by parsing and comparing exact canonical reserialization after strict UTF-8 decoding. It compares a full run with the independently discovered entire inventory and an individual run with exactly the requested single name. The wrapper's status message has separate fixed canonical framing and invocation identity; duplicate or missing messages are red. The Controller validates against its own invocation identity and commit, never trusts output logs as fallback authority.

Drain the endpoint concurrently with execution, with an inventory-derived maximum size sufficient for the canonical full name list and bounded framing, and enforce deadlines for both EOF and process closure. Multiple clients/messages of a given type, partial, oversized, late or extra data, broken pipe, cancellation, held-open channel or deadline are red. Terminate and reap owned process trees on error, release the lock, and retain diagnostic evidence. Specify exact byte bounds and deadlines in the implementation after checking OS argument and inventory limits; they must be deterministic, tested, and not silently truncate or reject a valid supported inventory.

For zero failures, proceed. For one or two failures, run every exact failed name alone under the same host-wide lock with fresh identities, compare the original SHA and check the current runner's substring selection matches exactly one file. All isolated records must be valid and show that one smoke passed. Three or more failures, an isolated failure or any missing, inconsistent or untrusted evidence leaves the gate red. Preserve the original log and each individual log, raw and validated records, all relevant exit statuses, expected SHA and disposition in fresh per-wave and per-invocation directories; persistence failure prevents push. Never overwrite earlier wave evidence or rely on shared runner failure-log names for retention.

Run the existing optional browser gate after the smoke disposition with both `GATE_SLOTS=1` and `GATE_E2E_SLOTS=1`, same host-wide lock, and propagate failure. Preserve skip/other-platform notices and independent browser review: aggregate success does not prove skipped browser flows. After browser completion, repeat source and inventory checks, bind final ref explicitly to the verified SHA and push with existing hooks; the earlier dry run is not push evidence. No live wave or full gate during development.

## Public-entry-point adversarial test plan

Use only invented fixtures, temporary git repos, a local fake remote and fake commands. Drive the real runner/npm command and the complete wave entry point; explicitly register or invoke new script tests rather than assuming `npm run test:scripts <file>` selects only that file. Test first, one observable slice at a time.

1. Zero, one, two and three parallel failures; all individual successes, each individual failure, wrong name and reused evidence. Check exact rerun names, identities and retained evidence; check the local remote ref, not merely a fake push exit. Three remains red.
2. Build failure after fake success text, runner spawn error, signal, missing result, partial record, invalid or contradictory status, npm pre/post failure, supervisor/outer-gate failure after plausible evidence, browser failure and final hook rejection: no push. Assert ordering and exact verified SHA.
3. Real child emits forged record and multiline runner-shaped output; it cannot authorize a pass. Cover missing, multiple, truncated, oversized, malformed UTF-8, duplicate keys/names, extra data, wrong schema/count/subset/inventory/commit/run identity, held-open channel, cancellation, timeout and locator/identity omission including retries. Verify bounded concurrent drain and process reaping.
4. Full tracked inventory versus actual entries, including missing, extra ignored or untracked, symlink and nonregular names; individual substring ambiguity; persistent HEAD/index/tree/inventory edits at every phase barrier. Demonstrate transient edit restored between checks is **not guaranteed detected** under cooperative option A.
5. Exercise actual npm local binary PATH and lifecycle variables and pre/post scripts, including failing hooks; preserve runner process status separately from npm status. Assert full default parallelism, individual exact selection and no silent verify command substitution.
6. Concurrent fake wrapper/lock fixtures demonstrate build plus complete parallel suite share one lock; individual and browser gates use the same serialization and browser slot settings. No live host lock experiment.
7. Preserve ordinary runner CLI, human summary stamp, failure details, retries and skip notices, and existing hooks; Linux-only evidence mode must not break ordinary supported-platform usage. After accepted implementation, run requested typechecks, affected suites and relevant browser specs through `gate`, merge origin/main and rerun affected suites; independent Tester performs full gates and review.
