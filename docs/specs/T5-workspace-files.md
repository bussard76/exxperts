## Authorized public contracts

All routes are under `/api/persistent-agents/:id/`; `id` is a usable room agent ID and the required, nonblank query `conversationId` selects the effective room/thread policy. URL-encode query values. Existing successful responses are HTTP 200. Normal room status and remote-device authorization also apply. Errors use JSON `{error: string, code?: string}`; policy errors may include `forbiddenRoot`, and a revision conflict also carries `currentRevision`. A missing `conversationId` returns 400 with `error: "conversationId is required"`. Generic errors default to 400, though an error with a status code keeps that status. Do not expose absolute workspace paths to remote clients.

- `GET workspace-files?conversationId=…&path=…`: `path` is optional, default root (`""`; `"."` also normalizes to root). Returns `{agentId, conversationId, root, path, entries}`. `root` is null, or `{displayLabel, basename}`; each entry is `{name, relativePath, kind: "file" | "directory", bytes: number | null, modifiedAt: ISO string, extension: string}`. Directories have null bytes and empty extension; file extension is lowercase. Directories precede files; names sort locale-aware, numeric, case-insensitively. No policy/grant or no `ls` yields `{root:null,path:"",entries:[]}`. Empty directories have an empty array. The branch excludes hidden and denied entries and symlinks, but its direct directory request and root fingerprint have the security gaps described below. Invalid relative segments/absolute paths produce 400; filesystem errors carry their existing code where present, and permission errors are 503 `workspace_unavailable`.
- `GET workspace-markdown?conversationId=…&path=…`: returns `{agentId, conversationId, path, content, encoding:"utf-8", bytes, revision, readOnly}`. Revision is `sha256:` followed by 64 lowercase hex digits of file bytes. `readOnly` reflects write mode and allowed `write`, `edit`, or `write_markdown_file` tool. Only an existing `.md` regular file is supported, case-insensitively; maximum 128 KiB, valid UTF-8, no NUL.
- `PUT workspace-markdown?conversationId=…&path=…` with JSON `{content: string, revision: string}` replaces the existing file and returns the same object as GET with new content, byte count and revision. It requires read and write access and a valid original revision. Existing code checks the revision before and immediately before atomic rename; a mismatch returns 409 `revision_conflict` with `currentRevision` and leaves the target untouched. The request never creates a file. Preserve these conflict and atomic replacement behaviors.
- `GET workspace-image?conversationId=…&path=…` returns image bytes with the extension-derived content type: `.png` `image/png`, `.jpg`/`.jpeg` `image/jpeg`, `.gif` `image/gif`, `.webp` `image/webp`, `.svg` `image/svg+xml`. Maximum 20 MiB. The response includes `content-security-policy: sandbox; default-src 'none'; style-src 'unsafe-inline'; img-src data:`, `x-content-type-options: nosniff`, `referrer-policy: no-referrer`, and `cache-control: no-store`.

For Markdown and image routes, input paths are workspace-relative, slash-normalized, nonempty, and reject absolute paths, `~`, NUL, empty, `.`, `..`, or dot-prefixed segments. Errors currently include 400 `invalid_path`, `unsupported_file_type`, `invalid_body`, or `not_file`; 403 `workspace_read_forbidden`, `markdown_write_forbidden`, `blocked_by_policy`, or `outside_workspace`; 404 `workspace_not_found` or `file_not_found`; 409 `revision_conflict`; 413 `file_too_large`; 415 `invalid_encoding` or `binary_content`; 503 `workspace_unavailable`; and 500 `workspace_file_error`. Other guarded tool errors map to 400 with their code. Image errors use this same mapping, including its Markdown-oriented missing-file message. Permission/unavailability errors must not become successful reads or writes.

## Required protections and differences from the branch

ADR-0002 requires the existing effective room grant and tool policy on **every** tree, Markdown and image access, including paired devices. Verify the grant's stored realpath fingerprint each time, reject a missing or retargeted root, and apply existing default and configured denied segments and filename globs, globally closed locations and write restrictions to the requested path and resolved target. Never follow symlink files or ancestors for Markdown or image access; tree listing must not follow symlink directories or disclose denied entries. Enforce the existing read mode and the specific tool permissions below; writes also require write mode and an allowed writing tool. A read-only paired device may use read routes according to existing remote policy, but cannot PUT; a device with write permission is still bounded by the room grant. Neither remote access nor a crafted direct request expands the workspace. The current tree independently resolves the root and misses the fingerprint and requested denied segments; correct that gap and apply equivalent guarded behavior, preserving existing successful shapes. Do not turn a denied or changed grant into a listing of another directory.

### Tool and mode authorization

For every local or paired request, require the effective room grant and read mode. Tree listing additionally requires the authorized `ls` tool. Markdown and image GET require the authorized `read` tool. PUT requires `read`, write mode, an authorized `write`, `edit`, or `write_markdown_file` tool, and the guarded file read and write policies for the requested path and resolved target. Device authorization remains an additional restriction. A tool or Bash being enabled does not substitute for the required tool.

With a usable grant, read mode enabled and all other path and device protections satisfied, the following matrix defines tool selection alone (`yes` for PUT also assumes write mode and a write-capable device):

| Selected tools | Tree GET | Markdown/image GET | Markdown PUT |
| --- | --- | --- | --- |
| Bash only | no | no | no |
| `ls` only | yes | no | no |
| `read` only | no | yes | no |
| A writing tool only | no | no | no |
| No tools | no | no | no |
| `read` and an authorized writing tool | no unless `ls` is also selected | yes | yes |

Disabled read mode denies all four routes regardless of tool selection. A denied tree listing keeps the empty-root response described above; denied file or image reads and writes must not expose content.

The current image resolver sends scheme and protocol-relative sources directly to the browser. ADR-0002 instead requires external images remain blocked: preserve their source/link in the file, show alt text, and send **no network request** on opening. Local image sources resolve relative to the Markdown file; leading `/` is relative to the workspace root, `.` and `..` are resolved without crossing that root, and URL-encoded spaces resolve to the intended filename. Unresolvable, missing, blocked, unsupported or oversized images must not expose other files or prevent the editor opening; show the image's alt text. Local paths still pass through the guarded image route. Keep the original Markdown source rather than replacing it with the route URL.

## UI and preservation requirements

The sidebar displays the granted folder and expandable tree, with loading, no connected folder, empty folder and error states. Selecting a Markdown file opens the right editor; dragging a file into the composer inserts its workspace-relative path at the insertion point. The existing editor offers Edit, Preview and RAW, loading, ready, saving, saved, unsaved, read-only, conflict and error states. It autosaves after a one-second idle period, supports explicit Save, and checks for external changes every five seconds. A clean external change refreshes; a dirty change presents Reload and Keep mine. Reload discards the draft for the latest version; Keep mine obtains the latest revision and attempts to save the draft, retaining conflict/error if unsuccessful. A failed save must not discard the draft. Before leaving a dirty editor, retain the existing save, discard, and cancel choices; a failed save keeps the editor open. Read-only files cannot be saved.

Issue #5 requires saving an edit to leave image Markdown unchanged, including linked images and paths with spaces. This is not limited to image-only links: `[text ![x](a.png)](url)` must retain its link and image source too. The branch is known to lose that link; it is a defect to correct, not an approved narrowing. Test a standalone image, an image-only link, mixed text and image in a link, and paths with literal and encoded spaces. Compare saved bytes against the original with only the intentional text edit; opening without editing must not rewrite the file. Do not claim a general guarantee for unrelated Markdown serialization that the issue did not decide; HTML `<img>` with attributes was not tested on the branch and remains an edge-case debt candidate unless needed to satisfy the stated image requirement.

## Acceptance tests (invented data only)

Run public HTTP routes against an isolated demo room and temporary workspace, plus a real web UI against that server; no real files, services or model APIs. Tests must exercise the actual route producers and browser consumers, not only helpers.

1. List root and nested `notes` directory, check response fields, ordering, empty and missing-workspace states; reject invalid traversal and direct denied-segment requests, hide denied filenames and dotfiles. Retarget the granted root after approval and verify all three read routes and PUT refuse access and reveal no replacement contents. Try symlink files and directory ancestors pointing inside and outside the workspace; none bypasses the existing guards. Exercise a protected write path as well as denied read paths.
2. GET and PUT `notes/plan.md`: assert all fields, UTF-8 byte count and SHA-256 revision, successful replacement, then stale revision 409 with current revision and unchanged file. Cover nonexistent file/workspace, invalid path/type/body/revision, disabled read, read-only write, oversized content, invalid UTF-8 and NUL. Verify 128 KiB boundary and no creation on PUT. For image route verify each supported content type, security headers, size boundary, missing/denied/unsupported path and no bytes from outside the grant.
3. Exercise authenticated paired read-only and write-capable mock devices on all four routes: read-only PUT is denied; write-capable PUT still obeys the grant and room tool permissions. For both local and paired requests, exercise Bash-only, `ls`-only, `read`-only, write-only, no tools, and disabled read mode on all four routes against the matrix above; also exercise `read` plus a writing tool and disabled write mode. Assert that denied reads return no file or image contents and denied PUT leaves the file unchanged. Verify the root and protected-path checks for local and paired access.
4. In the browser create a demo room with a temporary folder containing `notes/plan.md`, a local `images/blue sky.png`, and the preservation examples above. Expand the tree, open the file, observe the local image in the editor, edit unrelated text and save; compare file bytes to the original with only that edit. Drag the file into the composer and assert its relative path appears at the caret. Verify empty/no-folder/loading/error and read-only states. Simulate a failed save and an external revision change while dirty; check draft retention, Reload, Keep mine and dirty-navigation save/discard/cancel.
5. Open Markdown containing an external image pointed at a mock HTTP endpoint, including a protocol-relative source. Assert visible alt text, preserved source after an unrelated save, and zero requests to that endpoint while opening and rendering in Edit and Preview. Exercise missing and blocked local image paths without losing the editor or exposing bytes.
6. The independent Tester runs `npm run build && npm run smokes`, including `workspace-markdown-images-smoke`, `workspace-markdown-images-ui-smoke`, `composer-text-insertion-smoke`, `persistent-room-workspace-files-smoke`, and `persistent-room-workspace-markdown-files-smoke`. The preview acceptance remains: open a Markdown file with an image in a room with a folder, see the image, edit and save, and verify `git diff` shows only the edit and unchanged image line. Use invented files for automated checks; Sascha owns the real preview acceptance. A browser test skipped for missing Chromium is not evidence of a passing browser flow.
