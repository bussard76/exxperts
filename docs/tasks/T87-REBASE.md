## Private RoomBox binding

Owner: server workspace/file developer, coordinating `room-socket.ts`, `room-settings-routes.ts` and the existing room-file seam. On a Mac the target creates a `RoomBox` in the owning conversation connection's closure and supplies that instance to its file tools; HTTP handlers cannot reach it today. Bind that instance privately in process to its validated room and conversation identity when the connection owns it and is usable. This binding is ephemeral, never persisted or exposed to clients, and conveys no authorization: every route still validates the room, conversation, current policy and path independently. Do not create a substitute box for a request or borrow one from another conversation. A request with no unique current binding, including an ambiguous set of live owners, fails closed with 503 `box_failed` and no listing, bytes, parser invocation or host-read fallback.

The owning connection controls the binding's lifetime. Remove or invalidate it on owner close, conversation or room identity change, box disposal, and any loss of ownership; a detached turn may retain it only while the original owner remains the actual owner and the identities and box remain current. Reconnection or replacement registers a fresh binding; cleanup from an older owner must not remove its replacement. Give each binding an opaque generation or equivalent identity: obtain it after the folder wait, recheck it before boxed work and immediately before returning data, and reject an invalidated, replaced or ambiguous binding with 503 `box_failed` and no result. Cancel or discard in-flight results when ownership changes. Neither a previously valid tab nor a saved box reference proves the binding is current. On platforms and shared-server paths that do not use a Mac `RoomBox`, retain their existing specified fence, wait and read behavior; absence of a required Mac binding is never treated as the existing `inTheBox` startup-failure fallback. The existing fallback remains limited to an actual boxed-operation startup failure under the already stated before-any-command condition.

Verify through the public routes with invented fixtures: the right room and conversation use their owning box; missing, stale, removed, replaced and ambiguous bindings return `box_failed` with no data or host read; another room or conversation cannot borrow a binding; owner close and identity changes invalidate it; old cleanup cannot remove a replacement; and replacement or revocation while a bounded read is in flight suppresses its result. Exercise detach/reconnect and multiple-owner cases, and retain the existing policy, path, identity and box-failure checks. Use fake box dispatchers only where needed to observe which box was called and prove zero host fallback; keep the real browser-to-box acceptance path required below.

## Protection and listing/reading seam

Owner: server workspace/file developer; UI and worker consumers depend on this seam. Integrate within `persistent-room-workspace-tools.ts` alongside private `waited`, `inTheBox`, `callFence`, `guard`, `filesFor` and `room-box/box-files.ts`; do not revive source `resolvePersistentRoomWorkspaceExistingFile` or call `fs.readFile` on a source path from a route or parser. Route context supplies the validated `agentId`, existing `conversationId`, relative `path`, effective policy/fingerprint and current room box, folder wait and abort signal. Each call waits/holds the same named folders as file tools; obtains the current fence and box after waiting; applies `fencePath` and refusal checks, including each listing entry; uses `BoxFiles` for boxed roots, `openNoFollow` for shared-room files and `readOpened` for held beyond roots. Preserve `inTheBox` fallback: only before any boxed command since boot; otherwise `box_failed`, no read. The new private structured result carries entries `{name, kind, bytes, modifiedAt}` (directory bytes null), or a bounded Buffer plus identity `{real, root, dev, ino, size, mtimeMs, ctimeMs}`. The boxed file program must obtain listing metadata inside the box, not by a host-side stat of a room-writable name. Bound reads at the per-format limit below before allocating and while reading; a short, grown or replaced file fails. Worker parsers receive only a server-private temporary copy of those validated bytes, never the original path; cleanup on success, failure, abort or timeout. Keep existing source worker result validation and sandboxing.

For local rooms, `RoomFence` checks the chosen root's real path hash on every call and judges it again; `roots()` includes that root and currently sound Also allowed grants with their read/write access. Closed names, secrets, app state, links and denied paths stay closed. The source's relative single-root tree represents the chosen room root only: no synthetic selector, absolute path, or expansion to Also allowed, skills, spills, answer folders or beyond-root paths. Those remain accessible only through existing target tools under their existing policy, not through this UI. Shared server uses `roomFilesFence(agentId)`, the room's own shelf only, with `.` or one non-dot filename, no subfolders or stored local roots. On 0.16.2 Mac, iCloud Drive and account folders beneath `~/Library/CloudStorage` are eligible after the folder picker; `CloudStorage` itself is not; use `folder-offer.ts` current rules, never a new cloud exception. Moved, replaced, refused, unreadable, symlinked, or unavailable roots fail closed; an actually empty authorized listing returns `entries: []`, not an error or another room's files.

Before listing/read and immediately before returning data, re-fetch usable room, conversation and effective policy, rebuild the fence and compare policy fingerprint, root/path identity and resolved grant. For files compare device, inode, size, mtime and ctime around the bounded read and on reauthorization; for directories compare root and directory identity and reauthorize every retained entry. Revoked or changed authorization produces 403; changed identity produces 409, no bytes/results. Never assume an old UI tab is still authorized. A safe bounded snapshot that cannot be established fails closed. No protected paths or full host paths appear in results.

Refuse shell, DDE, delegate, URI, ambiguous placeholder, implicit or unresolvable working-directory forms; do not expand field codes other than one file placeholder (`%f`/`%u` on Linux only when the URI representation is the authorized local file, `%1` on Windows). ### Stored identity and qualification

Add to the selected local root in the existing policy file the private record `identity: { version: 1, kind: "fs-stat", platform: "linux" | "darwin" | "win32", dev: string, ino: string, birthtimeNs: string }`. Values are canonical unsigned base-10 integer strings with no sign, whitespace, leading zeroes or exponent; all three must be positive. Strictly decode the exact keys, tag, version, platform and values; reject unknown versions, additional fields, malformed, missing, zero or out-of-range values. Record bigint values directly from `fstat({ bigint: true })`, never a JavaScript number or rounded date. Compare all fields and the existing canonical real-path hash, with platform matching the running host. A matching tuple is evidence under the qualified filesystem assumptions below, not proof against deliberate metadata forgery or reuse of both an identifier and creation timestamp. Do not substitute mtime or ctime, or silently upgrade an unknown record.

At selection, resolve and validate the existing absolute path and folder rules, open the selected directory without following a final link where the platform supports it, and obtain identity and directory type from the opened object. Re-resolve the selected path and verify it still names that same opened object and canonical path before persisting; reject changes, links, inability to open or compare, and errors. At each authorization and revalidation repeat qualification and obtain current evidence from the actual selected directory object, not from the cached policy or fingerprint; hold the object through the check when supported and confirm the path still names it. These checks supplement, not replace, the existing path, policy and folder checks. If the required no-follow/handle-to-path comparison cannot be established on a platform, refuse; do not emulate it with a path-only stat.

Qualification is mandatory at capture **and** every recheck: the platform, actual mounted filesystem and provider must be identifiable using existing APIs, and their documented behavior must establish stable volume/device and object identifiers across restart for the grant's lifetime, a genuine sufficiently precise creation discriminator (not a fallback, rounded/default value or mutable change time), and a reliable comparison of the opened object to the selected path. Reject ambiguous mounts, overlays, remounts, network shares, cloud providers and virtual filesystems unless the actual combination meets all those conditions; a nonzero tuple, filesystem type name or matching samples alone does not qualify it. An unavailable API, unknown provider, uncertain timestamp provenance/precision, identifier reuse indistinguishable at that precision, changed evidence or any error is refusal. A changed volume/device after restart is refusal even if the folder is otherwise unchanged. Do not probe by modifying the selected folder.

The available evidence establishes **no generally supported platform/filesystem combination yet**. Node's [bigint stats and time semantics](https://nodejs.org/docs/latest-v22.x/api/fs.html#stat-time-values) document platform-dependent precision and that birth time can fall back to ctime or zero; Darwin birth time can also change when an earlier atime is set. Node's returned number alone does not identify that fallback. Microsoft's [file-ID documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information) says IDs can be reused and 64-bit IDs are not guaranteed unique on ReFS; [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) describes the distinct 128-bit identifier. Apple's [resource values](https://developer.apple.com/documentation/foundation/urlresourcevalues) may omit creation dates. These facts do not establish Node's fields as a trustworthy persistent identity on Linux, macOS, Windows, iCloud, or any named local filesystem. Consequently all such combinations are unqualified and fail closed unless implementation evidence establishes the full criteria above with the available APIs and no added dependency; do not infer support from operating system or a passing restart test. If no combination qualifies, do not claim that selection works or relax the rule: report the resulting product limitation to the Architect/Controller. A new representation or native dependency needs separate authorization.

### Refusal, selection and recovery

The pinned `validatePersistentRoomWorkspaceRoot` creates the path hash, `normalizePersistentRoomWorkspaceRootGrant` reconstructs known fields, and `readPersistentRoomDefaultCapabilityPolicy` returns null when policy normalization fails. Extend normalization and every read/write/rewrite, including conversation/default policy folding and the older-app rewrite, to preserve valid private identity exactly. Keep a configured root with absent, malformed, unknown or unqualified identity as an internal unusable grant; do not let normalization turn it into a null policy or drop the root. If the containing stored policy cannot be decoded at all, distinguish existing unreadable/invalid storage from an absent policy internally and fail closed; never manufacture an empty workspace. The existing `roomFolder`/`roomFence` moved/refused path supplies the refusal; map a configured but unusable root to the existing `folder_moved`/unavailable behavior and the specified route error, never `root: null, entries: []`. Preserve enough existing non-private view to let the person choose again, but expose no identity in views, responses, errors, logs, parser input or UI data.

Only a deliberate location choice submits a nonempty `root` to the existing PUT: the folder picker result or the submitted typed absolute path, including the same path. The server treats that existing root-bearing request as explicit selection, validates and captures a fresh identity, and atomically saves the new policy only after capture succeeds. A failed or indeterminate capture returns a generic existing folder refusal and leaves the previous policy unchanged. Startup, reads, normalization, policy rewrites and settings-only PUTs without `root` preserve the prior identity or invalid state and never capture a new one. Clear retains its existing meaning. Neither path equality nor a client-provided identity authorizes a folder.

For a lost selection response, the location UI reads the existing workspace-default view again. The pinned producer creates a fresh random `policyId` on each root-bearing save and the existing view exposes it; settings-only saves preserve it. Compare the before and after policy IDs, the requested selected path and the current refusal state: a new ID with the requested path and a usable current grant means the requested location is now selected, including same-path reselection. If the before state is unknown, the read fails, the ID is unchanged, the current path differs, or the grant is refused, report an indeterminate/failed save and allow retry; do not infer success from path alone. A concurrent independent selection may also change the ID: this check establishes the current desired state, not attribution to a particular request. No identity or new response field is exposed. Apply equivalent recovery to the no-folder picker in `App.tsx`.
